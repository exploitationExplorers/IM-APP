## 图 2：聊天请求失败 10005

已验证提供的测试账号：业务登录 HTTP 200/code 0，`GET me` HTTP 200/code 0，账号身份匹配。没有申请新的 IM token，没有发送消息或操作群。账号密码通过关闭回显的 stdin 临时传入，返回 token 只留在进程内存；本报告不记录手机号、密码、用户 ID 或 token。

OpenIM 官方 v3.8.3 `pkg/sdkerrs/code.go` 中，10005 是 `UnknownCode`，10004 是 `ResourceLoadNotCompleteError`。因此截图不能证明“资源未就绪”，也不能证明密码错误。当前固定的定制二进制未替换；仅依据官方定义区分通用数字码，不把官方源码检查说成本机复现证据。

发现并修复的客户端问题：

1. SDK 登录、全量会话和分页读取原先只显示同一段泛化错误，底层原因丢失。现在桥接层只保留固定操作名、数字码和白名单类别（未登录、资源准备、存储锁、结构异常、存储访问、磁盘满、超时等），不保存 SDK 原始消息或请求内容。调试资讯可查看及复制。
2. 全量读取遇到未知 10005 时，只尝试一次同 SDK 的分页读取；所有页面完整结束前不替换原列表，中途失败或重复页停止并保留旧列表，不伪造成功。
3. 资源未就绪/本地库暂忙时，使用独立于同步事件的有限重试：0.5、1、2、4 秒，最多四次。鉴权、结构、损坏、权限和磁盘问题不自动循环。
4. 原来 SDK 登录失败后，点击“重新读取”仍受 loggedIn=false 拦截，相当于无操作。现在点击状态按 SDK 真实登录状态处理；使用当前会话凭据重试连接，不签发新 token、不重建库。正在登录时不重复登录。
5. 读取失败时空状态显示“会话暂未读取成功”，不再把失败当成“暂无符合条件的会话”。

截图中的具体 10005 仍未在本机 SDK 重现，唯一根因尚未证实；上述更改修复已发现的布局、恢复和诊断缺陷。背景中的 hapticpattern 文件日志不能替代 SDK 失败证据。
