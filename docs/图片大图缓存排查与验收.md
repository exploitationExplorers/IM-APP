# 聊天大图缓存：修复范围与验收

## 1. 已确认的代码问题

- 原来的 `mediaCache` 只服务气泡缩略图/视频封面，并且只有 canary 渠道启用，不能视为大图持久缓存。
- 原 iOS 分支把部分远程图片下载到临时文件后交给系统图库，没有把预览下载结果写入可跨页面/重启复用的缓存。
- 大图失败/解码异常缺少明确重试界面，会表现为黑屏或一直等待。

这些是与反馈吻合、已通过代码和本地回归确认的缺口，**不等于已证明客户每张图片首次约 5 秒的全部网络原因**。首次下载仍受网络、文件大小、服务端响应和解码影响；本次不修改 OSS 签名，不承诺首次打开瞬间完成。源文件已经 404、签名过期、设备不支持的格式，也不能靠缓存自动恢复。

## 2. 本次实现

H5 和 App 统一进入 `pages/chat/image-viewer.vue`；小程序继续使用平台预览。

| 能力 | H5 | App（Android / iOS） |
|---|---|---|
| 持久缓存 | IndexedDB Blob | `downloadFile` → 校验 → `saveFile` + 索引 |
| 返回聊天后重开 | 复用内存/磁盘 | 复用内存/保存文件 |
| 刷新/重启后重新从聊天打开 | 从 IndexedDB 恢复 Blob URL | 从索引验证保存文件后复用 |
| 失败处理 | HTTP 状态提示、渲染失败/超时、手动重试 | 下载/解码超时、文件丢失重下、手动重试 |
| 交互 | 滑动、缩放、上一张/下一张、保存、Esc 关闭 | 滑动、双指缩放、按钮缩放、长按保存/保存按钮 |

- 缓存所有发布渠道启用，与旧缩略图 canary 开关无关。
- 同一用户、同一**完整 URL** 的并发下载合并；不会预下载整组原图。
- 只挂载当前原图，缩略图可用时作为加载占位。
- 持久化单文件最多 20 MiB，总预算 200 MiB，闲置 30 天失效，写入时按 LRU 淘汰。超限文件仍可显示，但不保证跨重启缓存。
- 用户命名空间取业务 JWT 的稳定 `uid`，不是 JWT 本身；无用户页面用 `public`。签名/查询参数是缓存键的一部分，链接变化会重新下载，不通过删签名来伪造命中。
- 设置页清缓存/退出登录会清理预览缓存；在途下载/写入有失效标记和串行写入屏障，避免清理后旧任务重新写回。仅处理预览缓存，不清空业务数据库或手机相册。
- 缓存不可用/配额不足时，尽量展示已下载图片，不把缓存失败当作发送失败。原生 `saveFile` 移动临时文件后的索引失败，也保留可用的保存路径。
- H5 第三方图片缺少 CORS 时可退回普通图片加载；该分支**不算持久缓存命中**，必须由图片事件/超时明确结束等待。当前 OSS 域名应允许前端来源的 GET/HEAD，否则 H5 不能获得完整的离线缓存效果。
- 预览导航只传一次性会话 ID，不把带签名的图片地址写进地址栏。直接刷新预览页会提示返回聊天重新打开；刷新后从聊天重开才是持久缓存验收路径。
- 本次保留消息字段的现有规范化链路，未改动 camelCase/PascalCase 兼容或 SDK 发送参数。

## 3. 已执行验证

前端目录：

```shell
npm run test:unit
npm run type-check
npm run build:h5
npm run build:app
python scripts/verify-h5-image-preview.py --base-url http://127.0.0.1:5191 --output-dir <仓库外证据目录>
```

最后一项需另开本地 Vite（`npm run dev:h5 -- --host 127.0.0.1 --port 5191`），安装 Python Playwright 并有 Edge；也可通过 `--browser-channel` 选择已安装的 Chromium 系浏览器。不发布 WGT。

- 128 项 Vitest 用例通过，涵盖 URL/用户隔离、重复下载合并、新实例磁盘命中、文件缺失、过期、损坏、403/404/500、缓存配额失败、清缓存与在途写入竞争、旧校验不得删掉新重试结果、原生回调缺失、导航会话和视频/转发/发送兼容。
- `vue-tsc`、H5 构建、App 构建通过。构建中的既有静态资源/分包警告不属于本次修复。
- 使用真实 Edge、390×844 与 1280×800 两种视口。仅使用本机合成图、不登录；阻断业务路径、外网 HTTP 请求及 WebSocket，避免本地 Vite 代理意外访问正式环境。
- 每组 17 张图片首次仅请求当前 1 张；实际拖动和按钮可遍历 17 张，没有请求未访问原图；反向浏览、关闭重开、整页刷新后重开均新增 **0 次原图服务端请求**。
- 图片服务明确返回 `Cache-Control: no-store`，因此上述刷新命中来自应用 IndexedDB，而非浏览器 HTTP 缓存。
- 两种视口的缩放按钮、关闭/Esc、缓存 Blob 保存下载、404 提示和恢复后的重试通过，无页面异常；H5 保存没有重新下载原图。

这是本地合成图片的缓存/UI 验证，**不是线上群聊或 iOS/Android 真机验收**。手机双指手势、相册权限、华为保存兜底及强杀重启后的缓存，仍需真机执行下表。

## 4. 手机验收（不需要清库）

1. 使用这次代码构建的版本，选一张刚发送且可访问的新图片，记录时间/系统/版本/网络。
2. 首次打开，确认有加载提示/占位、图片能显示；关闭重开确认不重复下载。
3. 返回会话列表再进群，打开同图；再强杀 App、重启登录后打开同图。预期优先复用缓存。
4. 预先加载成功后断网，同一 URL 的已缓存图应可查看；未缓存图应报错并能在恢复网络后重试。
5. 左右滑动、多指缩放、缩小后滑动、上一张/下一张、返回键、长按保存/保存按钮；拒绝相册权限后仍应能预览。
6. 设置清缓存后打开同图，应重新下载；登出换号不得命中前一用户的内存命名空间。
7. 对比慢图大小/类型，区分下载慢和下载后解码慢；不要只凭黑屏就认定 OSS 故障。

## 5. 仍慢时如何取证

调试版控制台启用：

```javascript
uni.setStorageSync('im_preview_debug', true)
```

只看 `[im:preview]`：`download`（下载阶段耗时/字节数）、`cache_hit`（memory/disk）、`asset_ready`（含缓存读写的文件就绪总耗时）、`display_ready`（含解码总耗时）、`load_failed` / `decode_failed`。日志不打印用户 ID、原图 URL、签名、JWT 或密钥。结束后：

```javascript
uni.removeStorageSync('im_preview_debug')
```

H5 可在开发者工具 Console 执行；App 需 HBuilderX 调试日志入口，不要求客户发送密码或证书。抓包截图请隐藏 Authorization、Cookie 和签名查询串。

- 下载耗时接近 5 秒：看同一请求的 DNS/TLS/TTFB/体积/传输速度，继续排查网络或服务端。
- 下载很快但 `asset_ready` 慢：排查缓存存储；文件就绪快但 `display_ready` 慢：记录图片类型/分辨率，排查解码和原生渲染。
- 同一用户、同一完整 URL 重开仍出现 `download`：检查清缓存、系统文件回收、存储配额/CORS，或实际 URL 是否刷新了签名；不要删签名参数来强行命中。
