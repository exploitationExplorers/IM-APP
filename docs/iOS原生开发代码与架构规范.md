# iOS 原生开发代码与架构规范

版本：1.0；更新：2026-11-17；适用范围：`IM-APP-ios`、其 Swift Package、ObjC 桥接及相关测试和构建配置。

本文是本项目的工程规则，供开发人员与 AI 编码代理共同遵守。参考 Swift 官方 API 设计指南、Google 公开 Swift 风格指南、Apple 的并发与性能文档，结合 IM 场景制定；不声称代表任何公司的内部规范，也不把某一种架构名称当作质量保证。

## 1. 执行等级与质量目标

- **必须 / 禁止**：代码审查门槛。涉及对应场景时不满足即应修复，不能以“编译通过”替代。
- **应当**：默认执行；有明确工程理由时可偏离，在变更说明里写出原因、影响和验证方式。
- **建议**：根据功能规模采用，不为满足形式增加无用层次。

优先保证业务正确、数据可靠、状态可解释、职责清楚和可验证，再优化复用与代码行数。禁止用吞错、清库、延迟碰运气或硬编码假数据掩盖故障。仅修改文档不代表既有代码已满足本文。

旧代码不要求一次性全部重写；新增代码必须遵守，修改旧代码时不得扩大原有问题。超出本次范围的存量问题记录位置、风险与后续处理条件，不阻塞无关小修复。

## 2. 架构与依赖方向

采用 UIKit + 按业务组织的模块 + 单向状态更新。页面复杂时使用 ViewModel / Presenter 管理展示状态，业务流程提取为 UseCase；简单页面不强制建立完整模板。

```text
App 装配层：创建具体实现、注入依赖、管理应用生命周期
  ├─ Feature / Presentation：ViewController、View、展示状态、路由
  ├─ Application：业务用例、跨组件流程编排
  └─ Infrastructure：网络、Keychain、文件、OpenIM 适配器
          ↓ 实现由内部需求定义的接口
       Domain / IMCore：值类型、业务规则、状态转换、必要端口
```

必须遵守：

1. 纯业务规则不依赖 UIKit、具体 SDK、App 单例或全局可变配置。
2. Presentation 不直接发送 HTTP、操作 Keychain、编解码 SDK 字典或操作 SDK 数据库。
3. Application 依赖业务所需的窄接口，具体网络和 SDK 实现由装配层注入。禁止跨层通过反射、通知或单例绕过依赖约束。
4. Infrastructure 将外部 DTO / SDK 对象映射为内部模型，外部类型不得扩散到全项目。
5. Feature 之间通过明确接口或路由交互，禁止引用其他页面私有实现或互相强持有。
6. 依赖图必须无环；不为每个 struct 建 protocol，也不为只有一次使用的代码建立通用框架。
7. 复杂度尚未达到拆包条件时，可先使用目录和访问控制建立边界。拆 Swift Package 的依据是独立职责、依赖与测试需求，不是文件数量。

现有 `IMCore` 是逐步整理的基础，不意味着目录中的全部代码已经纯领域化。已有网络与平台能力混放，应在相关变更时按职责迁移，避免仅为命名重写稳定功能。

### 推荐目录

```text
IMNative/
  App/                   入口、依赖装配、应用级路由
  Features/
    Conversation/        聊天页面、展示状态、页面组件
    Contacts/
    Account/
  Application/           发送、登录恢复等用例与编排
  Infrastructure/
    OpenIM/              SDK 适配与 ObjC 桥
    Networking/
    Persistence/
  SharedUI/              经实际复用的基础视觉组件
Packages/IMCore/         可独立测试的规则与状态
```

这是目标组织方式，不要求在功能修复中搬动所有现有文件。新增文件必须核对 Xcode target membership、工程引用和依赖链接。

## 3. 职责边界与防止大文件

### ViewController

仅负责视图生命周期、输入绑定、状态渲染与导航协调。不得同时承担 SDK 登录、网络重试、数据库、消息解析、媒体转码和页面渲染。

### ViewModel / Presenter

管理页面状态和用户意图；调用用例或受限服务接口。不得操作视图实例、持有其他控制器、直接实现底层存储协议。状态源必须明确，避免 UIView、控制器与 ViewModel 各存一套互相冲突的业务状态。

### Service / Repository / Coordinator

命名必须表达具体职责，例如 MessageHistoryRepository、SendMessageUseCase、SessionCoordinator。禁止把所有功能继续塞进 `Manager`、`Utils` 或通用 `Service`。Repository 不等于所有功能都必须增加一层转发。

### 本项目复杂度审查触发线

以下是本项目选择的审查信号，不是行业统一标准，也不是机械拆文件指标：

| 信号 | 要求 |
| --- | --- |
| 单文件超过 400 个非空非注释行 | 审查职责并说明是否需要提取；生成文件、表格数据等可例外 |
| 单个函数超过 50 个非空非注释行 | 检查是否混合多个业务步骤或副作用 |
| 嵌套超过 3 层 | 优先 guard、命名条件或独立规则，保持流程可读 |
| 一个类型混合 UI、网络和持久化 | 必须划清边界，无论行数多少 |
| 新增依赖或状态标记不断增加 | 检查是否缺少明确状态机或业务对象 |

禁止通过 extension 分文件、缩写命名或一行多语句隐藏复杂度。extension 只按协议实现或明确职责组织。

现有 `NativeIMService` 与 `NativeConversationViewController` 是重点治理对象：新业务不再默认追加进去；改动涉及的纯规则、媒体准备、历史加载或展示逻辑应优先独立提取。先补关键行为验证，再逐步替换，保留 SDK 单 owner、账号隔离和消息语义。

## 4. Swift 与 ObjC 编码要求

- 遵守 Swift API Design Guidelines，以调用处清晰为目标；类型 UpperCamelCase，成员 lowerCamelCase，Bool 表达判断含义。
- 一行一条语句，禁止分号拼接多条业务语句；命名表达含义，避免 `data`、`obj`、`flag1` 等缺少上下文的名字。
- 优先 `let`、值类型和最小可见性；类无继承需求时使用 `final`。共享可变引用需有明确隔离策略。
- 对外接口显式表达参数单位、时间语义、ID 类别及失败方式。时间戳区分秒/毫秒；业务 userID、IM userID、conversationID、clientMsgID 不混用。
- 使用具体模型、enum 和必要的强类型 ID；`[String: Any]`、`Any` 只允许停留在 SDK/遗留协议边界，进入业务前完成校验与映射。
- 禁止生产业务路径 `try!`、`as!` 与未经证明的强制解包。UIKit 初始化等已证明的不变量可局部使用，说明成立条件。
- `fatalError` / `preconditionFailure` 只表达不可达的程序错误；不得处理网络失败、坏消息或用户输入。程序化 UIKit 的不支持 coder 初始化属于允许的局部场景。
- 不通过大量默认空字符串、0 或 false 隐藏必填字段缺失。可选、未知、无权限、失败必须保留不同含义。
- 魔法数字提取为有单位和含义的常量；协议值用 enum 或集中映射，未知枚举值有兼容策略。
- 注释说明约束、原因、边界和兼容背景，不复述语句。TODO 必须说明待解决问题与完成条件，不写“以后优化”。
- ObjC 桥只做类型、selector、错误和回调适配，不嵌入页面或业务策略。可公开头文件须定义 nullability、错误及回调线程约定。
- 第三方源码和生成产物不按普通源文件格式化；改动前确认来源。

## 5. 并发、取消与生命周期

1. UI 与展示状态在 `@MainActor` 隔离。禁止认为标记 MainActor 后函数里的同步工作就自动转到后台。
2. 图片解码、哈希、大 JSON 解析、文件读写和大集合处理不能阻塞主线程；使用适合的 actor、队列或明确的执行器策略，必要时测量实际执行位置。
3. 跨隔离域的数据满足当前编译器的 Sendable 约束。禁止用 `@unchecked Sendable`、`nonisolated(unsafe)` 或关闭检查掩盖竞争；例外需说明锁/隔离不变量并验证。
4. 优先结构化并发。无结构 `Task` 必须说明 owner、存活时间、取消与错误去向；`Task.detached` 仅用于明确需要独立执行上下文的工作，不能作为万能“放后台”。
5. 页面消失、退出账号和切号时，按业务所有权取消相关工作。取消只是信号，回写前仍检查账号代次、请求标识及目标状态，拦截迟到回调。
6. 需要持久执行的发送任务归账号级服务所有，不能因页面关闭随意丢失，也不能在退出后继续污染新账号。
7. 回调转 async 使用 checked continuation；成功、失败、超时和取消只能完成一次。明确超时是否取消了 SDK 操作，不能把本地超时等同服务端失败。
8. 禁止主线程 semaphore 等待异步结果、同步跨队列互等、裸 `sleep` 碰运气或固定延迟代替就绪状态。
9. 每个 observer、timer、Task、闭包明确释放和取消位置；`[weak self]` 根据所有权选择，不能作为生命周期管理的替代。
10. 不默认启用 Swift 6 模式或抬高部署版本。并发迁移需兼容当前 Swift 5.9 工程与固定 SDK，分阶段消除警告。

## 6. 状态、网络与错误

- 有关联的状态使用 enum 及关联值，避免多个 Bool 组合出不可能状态。区分初次加载、已加载空结果、刷新、保留旧数据的失败与结束分页。
- 用户输入转换为动作，动作触发状态转换或用例，渲染消费确定状态。渲染本身不得偷偷启动请求或写持久化。
- 错误分层表达：网络/协议、认证、权限、持久化、业务拒绝、取消、未知结果。用户提示与诊断详情分别组织。
- 禁止 `catch {}`、无解释的 `try?`、错误返回空数组、把请求失败标记为“没有更多”。有意忽略的错误必须是可选行为，并说明降级与诊断方式。
- DTO 解码、状态码校验、鉴权、超时与请求构建集中管理；不在每个页面复制 URLSession 和 token 拼接。
- 重试须限定次数与时间预算，使用可取消退避；只自动重试已确认幂等或有幂等键的操作。禁止无条件重试发送、支付、注销等写操作。
- token 刷新合并并发请求，限制刷新次数；迟到 401 不得清理新登录态。普通 SDK 断线不循环签发 token。
- 分页请求具备请求标识、账号上下文、去重键、游标推进和结束依据；响应乱序、重复页、游标不推进有明确处理。

## 7. IM 可靠性与跨版本兼容红线

以下规则优先于一般的代码简化或架构调整：

1. SDK 仅有一个明确 owner；业务登录、SDK 登录、数据库就绪、同步状态分别管理，不用一个 `isLoggedIn` 代表全部。
2. SDK 独占历史数据库。禁止私自读写 SDK 表、建立第二套全量历史库或靠删库修复同步问题。
3. Outbox 在发送前原子持久化，写盘失败不得发送；稳定 clientMsgID 贯穿重试、查询与去重。SDK 接受不冒充送达，送达不冒充已读。
4. 超时、强杀、断网后的发送结果可能未知；先按 ID 核对，不因本地查询为空就自动重发。状态必须表达“未知/待核对”。
5. 账号和环境隔离存储、缓存与异步回调；退出先停止旧 owner，再创建新 owner，避免交叉登录与旧回调污染。
6. 可见水位与成员清理边界单调推进，历史迟到不能恢复已隐藏内容。首轮同步前的空页不能永久认定为历史结束。
7. 消息映射兼容历史 camelCase / PascalCase，在唯一边界统一规范化；未知字段和未知消息类型安全降级，不静默丢掉整条消息。
8. H5 SDK 存在的能力不能推定原生 SDK 存在。按固定版本正式接口实现，不伪造参数、不创建替身冒充正式验证。
9. 媒体 URL 不得无条件删除 query、重签或改写未知签名；缓存键与访问凭据分开设计，遵守过期、访问范围及 no-store 语义。
10. 后台执行与推送受系统限制。禁止承诺 App 永久在线；登记 push token 不等于 APNs 链路可用。

## 8. UIKit 与性能

- 优先 Auto Layout、safe area、trait 与尺寸约束，不假定屏幕尺寸、状态栏高度或键盘高度。原有手工布局可保留，但必须响应容器尺寸变化。
- 支持项目约定的文字缩放、VoiceOver 标签与操作、合理点击区域和颜色对比；视觉规范未覆盖深色模式时明确产品策略，不盲目混用动态色。
- 列表使用稳定 ID 与增量更新。禁止每条 SDK 事件全量 reload、同步解码全部头像或对整段历史重复排序。
- Cell 复用取消旧加载；回调核对资源与模型身份，避免头像错位。预取、解码、下载与缓存都有并发和容量边界。
- 大图按显示目标降采样；GIF、视频缩略图、文件扫描设置资源上限和降级策略。禁止把全部媒体一次性载入内存。
- 图片尺寸变化、键盘弹出和加载历史保留合理滚动锚点；用户已上滑时不得强制跳到底部。
- 性能结论以设备和场景测量为依据。记录设备/iOS、样本量、首次与热启动条件、历史规模、耗时分位与内存峰值；不虚构“流畅”或“零卡顿”。
- 关键路径使用 Instruments、Time Profiler、Allocations、Memory Graph 或 signpost 定位；工具选择随问题而定，不要求每次小改全跑。

## 9. 持久化、安全与隐私

- token 等凭据使用 Keychain，并明确可访问时机、设备绑定与迁移策略。密码不持久保存，密钥不硬编码、不提交仓库。
- 日志不得包含 token、密码、完整聊天内容、私密文件路径或带访问凭据的 URL；错误日志同样脱敏。关联 ID 需考虑用户隐私。
- 自有数据采用可验证的原子写入或事务；定义 schema 版本、失败恢复、空间不足和升级兼容。解码失败不直接覆盖原文件。
- 账号缓存按 owner 隔离；明确退出清理范围，禁止无边界删除目录。需要保留的待发记录和用户文件遵守产品策略。
- 文件名和路径来自外部时验证目录边界与类型，不信任扩展名、MIME 或服务器字符串；图片/压缩内容限制大小与资源使用。
- 使用系统 TLS 校验，不为修复网络问题全局放开 ATS 或忽略证书错误。
- 相机、相册、麦克风等按需请求权限；拒绝后提供可理解的降级。声明与实际调用一致。
- 新 SDK 检查来源、许可证、隐私清单、最低系统、体积和维护成本，锁定依赖并说明引入理由。

## 10. 测试与验证要求

按风险选择测试，禁止为行覆盖率写镜像实现、只测 mock 自己或只断言不崩溃。

| 改动类别 | 最低有意义验证 |
| --- | --- |
| 纯规则、解析、状态转换 | 针对边界、异常及兼容数据的单测 |
| 并发、账号切换、分页 | 可控制时序的测试，覆盖迟到、重复、取消与乱序 |
| Outbox、存储、迁移 | 写入失败、重启恢复、幂等与旧数据样本 |
| SDK/ObjC 桥 | 实际固定 SDK 编译链接；关键行为真机集成验证 |
| UI/布局 | 受影响流程、尺寸与键盘验证；必要时 UI/快照测试 |
| 小范围文案/格式调整 | 针对性人工检查，不新增镜像测试 |
| 性能修复 | 可复现场景和前后对比，不能仅从代码推断收益 |

测试禁止真实 sleep 等待随机时序，应注入 clock、ID、网络和存储等实际需要控制的边界。单测 fake 仅用于测试，不替代生产 SDK，不作为真实集成验收证据。

当前可用命令（仓库根目录）：

```bash
python3 IM-APP-ios/scripts/verify_project.py
swift test --package-path IM-APP-ios/Packages/IMCore
bash IM-APP-ios/scripts/verify_on_mac.sh
```

先理解脚本覆盖范围，再运行与改动有关的检查。IMCore 测试不能证明 UIKit 和 SDK 集成正确；没有 App XCTest target 时，空的 Xcode TestAction 不能当成功证据。模拟器通过不代表真机、APNs、后台、覆盖升级或旧库迁移通过。记录实际执行结果及未验证范围。

## 11. 格式工具、静态检查与 CI

- 当前规范不等于项目已安装 SwiftLint / formatter。引入工具时固定版本、提交配置，在本地与 CI 使用同一规则。
- 格式化只覆盖本次相关代码；存量全库格式化独立提交，避免掩盖业务 diff。
- 优先检测强制转换、无意义复杂度、死代码和危险并发；lint 禁用须局部并说明原因，不全局关闭来通过检查。
- 对新增代码要求无新增编译警告。既有警告基线按范围治理，不直接全局开启 warnings-as-errors 导致依赖无法构建。
- CI 按能力执行工程检查、IMCore 测试、模拟器编译；发布流程另做真机架构、签名和依赖校验。未接入的检查不能写成已经执行。
- Release / Archive 门禁、签名身份和迁移约束不能被格式整理或架构重构顺手删除。

## 12. 重构方式与变更说明

每次重构只围绕可说明的职责边界推进：确认现有行为 → 为关键语义补保护 → 提取接口/规则 → 替换调用 → 清除旧路径 → 验证。不要并行保留两套互相不一致的状态源。

禁止：无关全库重命名、为拆文件制造循环依赖、引入庞大框架解决小问题、将新旧功能一起重写后只做启动检查。确需大型重构，先形成迁移步骤与回退边界。

变更说明至少包含：解决的具体问题、最终行为、主要边界/取舍、已执行验证和剩余限制。描述结果，不仅列文件名。不宣称未执行的真机或性能验证通过。

重要架构选择以简短 ADR 记录背景、决定、替代方案和代价，例如数据库所有权、SDK owner、模块依赖或导航策略；一般函数拆分无需写 ADR。

## 13. 合并前审查清单

仅检查与本次改动相关的条目；不适用的无需制造形式材料。

- [ ] 职责清楚，没有继续扩大巨型控制器或通用服务。
- [ ] 依赖方向正确，SDK 字典和外部模型止于边界。
- [ ] 新增异步工作有 owner、取消、错误处理与迟到结果防护。
- [ ] 状态能区分失败、空、加载、结束和发送未知结果。
- [ ] 没有主线程重任务、无界缓存/并发或全量重复刷新。
- [ ] 没有吞错、强制转换、硬编码秘密或假数据冒充业务结果。
- [ ] 账号隔离、Outbox、SDK 库所有权和历史可见边界保持正确。
- [ ] 存量消息命名及媒体 URL 兼容未受破坏。
- [ ] 新文件进入正确 target，固定 SDK 和部署版本仍兼容。
- [ ] 执行了有意义的验证，明确模拟器与真机证据边界。
- [ ] 发布门禁与签名流程未被无意改变。

数据丢失、跨账号污染、重复发送、凭据泄露、崩溃与无法恢复的错误属于阻断问题。单纯超过行数触发线应审查职责，不能把机械行数等同缺陷等级。
