# 原生内测分发与更新

当前 Android 构建版本为 `0.3.3-media` / `versionCode 7`，应用身份是 `com.im.nativebootstrap.staging`。它与旧 uni-app 正式版并存。这里新增的脚本和工作流只准备独立原生分发文件；本轮没有上传安装包、部署下载站或修改线上后端。

## 用户以后怎样安装与更新

- Android：首次打开固定 HTTPS 下载页安装原生内测包。配置入口后，每次 App 进程启动最多自动检查一次，有新版才提示；检查失败静默，不影响登录和聊天。也能在 App「个人中心 → 设置 → 关于我们 → 检查更新」手动检查。下载并校验后由用户确认安装，需要时允许该 App 安装未知来源应用，返回再点「安装更新」。不能静默安装。
- iPhone / iPad：首次通过真实 TestFlight 邀请链接安装，后续在 TestFlight 中更新，也可开启 TestFlight 自动更新。正式审核上架后通过 App Store 更新。不能用下载 IPA 代替 TestFlight 或 App Store。
- 固定页继续保留同一个地址，APK 使用带版本和摘要的独立文件名。用户无需每次找新的临时下载链接。每次更新需要完整 APK，不能发布 uni-app 的 WGT。

## 与旧线上用户的边界

独立原生清单使用 `channel=native-staging`，不向现有后端的 `canary/test/prod` 发布记录写入 APK。旧 `/public/app-release` 响应没有包名、原生标识或签名信息，因此新「关于我们」未配置独立清单时会提示入口尚未开放，不会把旧壳候选包推荐为原生更新。

本功能不需要修改后端 API、数据库、旧前端或线上发布设置。正式替换旧应用仍需另外确认旧包名、签名与本地数据迁移，现有 Gradle Release 阻断继续生效。本方案的原生内测分发不代表正式应用已经可以原地替换。

## 第一次需要准备的实际资料

1. 一个可长期使用的 HTTPS 目录地址，由你们控制的 Nginx、OSS/CDN 静态站或 GitHub Pages 托管。路径必须独立于现有官网下载页；不要覆盖现有站点根目录。本仓库没有虚构已存在的托管地址。
2. 本批 Android 内测包使用的稳定签名 keystore、alias 和密码，以及证书 SHA-256。已交付本地测试包的 keystore 位于 `D:/jiedan/IM/.native-cache/android/debug.keystore`；不要删除或每次重建。它仅用于原生内测，不能当正式生产签名方案。若切换到不同证书，现有内测包无法覆盖更新。
3. iOS 需 Apple Developer 账号、App Store Connect 对应 App、正确 Bundle ID、签名与构建上传权限。创建并开放 TestFlight 测试后，才有真实邀请链接；当前未提供，页面不显示虚构链接。

签名证书 SHA-256 可这样核对，命令会提示输入 keystore 密码，不在命令行填密码：

```powershell
D:/JDK17/bin/keytool.exe -list -v -keystore D:/jiedan/IM/.native-cache/android/debug.keystore
```

本次已交付 Android 测试包的签名证书 SHA-256 为 `b79662c40f3611139311dc8080fda4712443555d339d405b332fe8e1cbf8ca0b`。后续工作流必须使用与已安装内测包相同的证书。证书指纹是公开校验值，不包含私钥。

## Windows 本地打包和准备下载站

以下路径均在 D 盘。先把真实托管地址和签名参数放入当前终端的环境变量；密码从你们的秘密管理方式注入，不保存到代码、Git 或网页目录。

```powershell
Set-Location D:/jiedan/IM

# 先填写真实、独立、长期保留的 HTTPS 目录地址。
$nativeDistributionBase = Read-Host '原生内测下载目录 HTTPS 地址'
$nativeDistributionBase = $nativeDistributionBase.TrimEnd('/') + '/'
$env:NATIVE_DOWNLOAD_PAGE_URL = $nativeDistributionBase
$env:NATIVE_UPDATE_MANIFEST_URL = $nativeDistributionBase + 'update.json'
$env:NATIVE_ANDROID_KEYSTORE = 'D:/jiedan/IM/.native-cache/android/debug.keystore'
# NATIVE_ANDROID_STORE_PASSWORD、NATIVE_ANDROID_KEY_ALIAS、NATIVE_ANDROID_KEY_PASSWORD
# 由操作员从秘密管理方式注入。四项签名参数必须一起设置。

./IM-APP-android/build.ps1 -Tasks @(':app:testDebugUnitTest', ':app:assembleDebug', ':app:lintDebug')

python -X utf8 scripts/native/prepare_distribution.py `
  --apk IM-APP-android/app/build/outputs/apk/debug/app-debug.apk `
  --base-url $nativeDistributionBase `
  --out .native-cache/distribution/site `
  --aapt D:/Android/SDK/build-tools/34.0.0/aapt.exe `
  --apksigner D:/Android/SDK/build-tools/34.0.0/apksigner.bat `
  --expected-certificate-sha256 b79662c40f3611139311dc8080fda4712443555d339d405b332fe8e1cbf8ca0b `
  --changelog-file docs/原生内测更新说明.md
```

后续发布应先从已上线的固定地址保存当前 `update.json` 到 D 盘，再加 `--previous-manifest .native-cache/distribution/previous.json`。脚本拒绝换签名、同版本号或降版本号发布。若回退代码，应重新构建更高 `versionCode` 的包。

生成目录包含 `index.html`、`update.json` 和不可变文件名 APK。`_headers` 是部分静态托管服务支持的缓存配置；Nginx、OSS/CDN、GitHub Pages 不一定识别它，需要分别配置。目录里不会包含 keystore 或密码。

上传顺序为：新 APK → 网页 → `update.json`。先保留旧 APK，最后替换清单，避免下载过程中找不到文件。给 `index.html`、目录入口和 `update.json` 设置 `Cache-Control: no-store`；APK 可使用长期 immutable 缓存。若托管平台默认规则不可修改，需实测并清理其 CDN 缓存。自有 Nginx 可对独立原生下载目录配置如下规则，实际路径由运维填写：

```nginx
location = /native-test/ { add_header Cache-Control "no-store" always; try_files /native-test/index.html =404; }
location = /native-test/index.html { add_header Cache-Control "no-store" always; }
location = /native-test/update.json { add_header Cache-Control "no-store" always; }
location ~ ^/native-test/native-[A-Za-z0-9.+_-]+\.apk$ {
    default_type application/vnd.android.package-archive;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
}
```

`/native-test/` 是配置示例路径，不是已部署入口。部署下载站只更改独立静态目录，不重启或替换业务后端。

## GitHub Actions 的稳定打包和可选托管

新增 `.github/workflows/native-distribution.yml`，仅 `workflow_dispatch` 手动运行。先在仓库配置：

| 类型 | 名称 | 内容 |
|---|---|---|
| Secret | `NATIVE_ANDROID_KEYSTORE_BASE64` | 同一内测 keystore 的 Base64 内容 |
| Secret | `NATIVE_ANDROID_STORE_PASSWORD` | keystore 密码 |
| Secret | `NATIVE_ANDROID_KEY_ALIAS` | 签名 alias |
| Secret | `NATIVE_ANDROID_KEY_PASSWORD` | 私钥密码 |
| Variable | `NATIVE_ANDROID_CERT_SHA256` | 对应签名证书 SHA-256 |

将内测 keystore 的 Base64 内容直接放入 Secret，勿写到仓库。CI 缺任意签名资料会失败，不会临时生成另一把 debug key。临时签名文件在任务结束时删除。

手动运行时填入真实 `distribution_base_url`。工作流将同一地址编入 App，并读取该站旧清单：404 允许首次发布，其他读取失败停止；旧清单存在时校验签名和严格递增版本。通过单测、构建、Lint 和 `apksigner verify` 后，产物 `native-staging-download-site` 是可整体上传的静态站目录。

默认 `deploy_to_github_pages=false`，只准备产物。若明确选择 GitHub Pages：先在仓库 Settings → Pages 将 Source 配为 GitHub Actions，确认实际完整页面地址与 `distribution_base_url` 完全一致，再勾选部署。若此仓库的 Pages 已用于其他站点，不要将本下载站部署到该 Pages 根目录；选择独立仓库或你们控制的独立静态目录。

`testflight_public_url` 和 `appstore_url` 都可留空。提供时必须使用实际 Apple 链接，生成器只接受正确的 Apple 域名和应用路径。执行工作流和部署需由后续发布操作完成，本轮未运行远端工作流。

## iOS 上传与更新步骤

1. 在 Mac 上安装 Xcode，确认 Apple Developer Team、Bundle ID、签名证书及 provisioning profile。iOS 工程当前 Release/Archive 仍有正式发布门禁，需要负责发布的人完成身份与迁移核验后按工程流程解除，不能绕过门禁打出“正式包”。
2. 执行 CocoaPods 固定依赖安装，打开 `IM-APP-ios/IMNative.xcworkspace`，选择真机目标，确认版本号与递增 Build Number；先完成模拟器、真机和真实账号验证。
3. Xcode 的 Product → Archive，Organizer → Distribute App → App Store Connect → Upload。首次上传处理完，在 App Store Connect 的 TestFlight 设置测试信息、出口合规和测试账号。
4. 内部测试先添加内部测试员；外部用户进入外部测试组，首次可能需要 Beta App Review。审核并开放后启用 Public Link，复制 `https://testflight.apple.com/join/实际邀请码`。
5. 将真实邀请码填入下载站生成器/工作流。App 内可通过 iOS 构建设置中的 `NATIVE_TESTFLIGHT_URL`、`NATIVE_APPSTORE_URL`、`NATIVE_UPDATE_MANIFEST_URL` 编入真实入口；清单的 `ios` 对象同样提供两个 Apple 链接。打开链接后由 TestFlight / App Store 管理安装更新。
6. 后续继续上传同一 App 更高 Build Number，在 TestFlight 选择测试组。TestFlight 构建有效期通常为 90 天，过期前上传新包；正式分发需另外完成 App Store 审核与发布。

当前没有 Mac/Xcode 构建、Apple 凭据、真实 TestFlight 邀请、固定托管地址或已部署站点，因此以上是可执行发布流程和配置入口，不表示 iOS 包或下载站已经上线。

iOS 的以上三个变量是 Xcode Build Settings 的 User-Defined 项，不是仅在 Terminal 中 `export` 就一定会编入包的变量。也可在 `xcodebuild` 命令末尾显式传入 `NATIVE_UPDATE_MANIFEST_URL="https://你们实际托管目录/update.json"` 等构建参数。Info.plist 使用对应的构建变量展开；全部为空时，“关于我们 → 检查更新”会说明入口未配置，不会跳到其他应用或旧 uni-app 包。链接只接受指定 App 的 Apple TestFlight 邀请页和 App Store 页面，不下载或安装 IPA。

## 发布前确认一次完整更新链路

用两台 Android 真机，先安装较低版本原生内测包，再发布同证书更高 `versionCode` 的包：固定页应显示新版本，App 应检查到更新，授权后能覆盖安装，并保留当前原生账号和本地数据。分别验证网络中断、坏 SHA-256、不同证书、错误包名、旧 uni-app 包和已清理的缓存包均不能作为有效更新。

iOS 应用实际 TestFlight 测试账号完成一次低 Build → 高 Build 更新，再验证登录、同步与聊天数据。静态脚本通过不代表这些设备链路已验收。
