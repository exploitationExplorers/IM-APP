SDK 把 null 推送参数编码为空字符串，已由本机实际依赖的 JVM 测试确认。这是发送参数缺陷的证据，不能据此声称已证明每个现网发送失败都只有这个原因。未取得真实账号或现网原始慢图，不虚构服务端错误码、耗时或吞吐结果。

“待核对”是客户端 Outbox 的不确定发送状态，并非内容审核。超时后做有次数上限的本地查询；明确失败才显示手动重试。重试先查同一 clientMsgID 的结果，确认尚未发送成功后才重新提交原消息；不自动盲重发。旧回调不能覆盖新一次发送状态，实时成功回执也能完成业务回调，防止转发一直转圈。

## 为什么本地有聊天记录还会加载图片

消息库通常保存消息文字、顺序和图片地址；图片文件另有下载缓存。首次接收、文件被清理或服务器图片地址不可用时，仍需要网络。已缓存且仍有权限的图片应直接复用；本轮补的是缓存复用、旧字段恢复和失效回退，不能把“本地有消息”当作原图必然已完整下载。

Android 新登记的本地图仅来自本 App 私有 outgoing 目录里本次真实上传成功的文件，按账号隔离，不信任消息携带的任意本地路径；有容量、数量与保留期限限制。此项不等于“上传前立即生成本地气泡”或完整持久化上传队列，后者仍属于性能方案的后续阶段。

## 拿到新包后的复测顺序

1. Android 覆盖安装本轮 APK，确认诊断页显示 0.3.2-parity；不要先卸载或清数据，以免丢失待发送状态和缓存。它使用原测试包名，不覆盖旧 uni-app 正式包。
2. 进入问题聊天：首次打开后退出再进、结束进程后再进，分别观察同一张图；记录未显示的是哪条消息与大概等待时间。首次网络下载不能要求无网络也秒开。
3. 两个测试账号互发文本与图片，确认接收方收到；再将旧图片转发给自己、好友和群，避免只看发送方成功图标。若停在待核对，进入诊断页记录 SDK 错误码，先核对，不连续反复重发。
4. 依次验证文本、图片、视频、文件、名片的长按菜单；普通成员、管理员和群主分别验证权限；验证单条转发、多选转发和删除。保存媒体要实际确认相册权限与文件结果。
5. 通讯录从顶部持续滑到底，搜索栏固定，其余内容一起滚动；对照 uni-app 页面检查间距、排序和分页。
6. 在 Mac 解压本轮 ZIP，执行 `bash IM-APP-ios/scripts/verify_on_mac.sh`。通过后运行 iPhone，重点验证大历史库同步、切后台恢复、断网重连、账号切换和上述收发/菜单场景；保留 `verification/mac/` 日志。
