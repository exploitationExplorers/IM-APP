# 群容量与群聊已读技术实施文档

## 1. 目标与口径

- 群人数由管理后台配置；技术安全上限来自环境变量 `GROUP_MEMBER_HARD_LIMIT`，缺省 4000，不在代码或数据库 CHECK 中固定 2000/4000。
- 有任意一名其他成员读到发送者的群消息，即显示“已读”。UI 与私聊一致：未读单勾、已读双勾。
- 降低上限不会踢出现有成员。群处于超限状态时，只禁止继续新增，直到成员数回落。
- 批量邀请容量不足时整批拒绝，不做部分成功。

## 2. 容量模型

```text
effectiveLimit = min(groups.max_members,
                     published.system.limits.maxGroupMembers,
                     GROUP_MEMBER_HARD_LIMIT)
```

新群的 `groups.max_members` 取已发布的 `defaultGroupMaxMembers`。默认配置为平台 500、新群 200，环境技术安全值 4000。管理后台保存草稿时校验 `3 <= 新群默认上限 <= 平台上限 <= 技术安全上限`。

所有新增入口在锁定 `groups` 行后判断容量：建群、开放加入、扫码加入、邀请、接受邀请和审批入群。批量邀请先计算去重且有效的候选集合，再一次性判断剩余容量。

单群修改通过静态写接口 `POST /api/admin/v1/group-member-limits/update`，请求体为 `groupId/maxMembers/reason`。server 内部对应 `POST /internal/admin/group-member-limits/update`。变更写入 `group_member_limit_logs`，保留旧值、新值、当时人数、平台上限快照、操作者和原因。

## 3. 群聊已读模型

旧方案查询一次会遍历全部群成员，并对每个人调用 OpenIM；4000 人群会放大成约 4000 次上游请求。新方案只保存“阅读者在群会话中的最新游标”：

1. APP 打开群会话后先调用 OpenIM SDK `MarkConversationMessageAsRead`。
2. APP 以 1 秒防抖调用 `POST /api/v1/im/group-read-cursors/report`。
3. server 只向 OpenIM 查询当前用户一次 `hasReadSeq`，以 `GREATEST` 单调写入 `im_group_read_cursors`，同时更新 Redis ZSET。
4. 发送方仅在存在自己发送且尚未读的可见消息时，每 5 秒调用 `GET /api/v1/im/group-read-state?conversationId=...`。
5. server 从 Redis 最高两个分值中排除发送者；缓存未命中时使用 PostgreSQL 索引查询其他成员最大游标。
6. `message.seq <= maxOtherReadSeq` 时表示至少一人已读。全部当前可见的自己消息变为已读后停止轮询，页面隐藏或卸载也立即停止。

上报固定为 1 次 OpenIM 请求，状态查询不调用 OpenIM，复杂度不随 2～4000 人线性增长。

## 4. 数据表与索引

迁移 `IM-APP-server/migrations/032_group_capacity_and_read_cursors.sql` 新增：

- `im_group_read_cursors(conversation_id, group_id, user_id, has_read_seq, updated_at)`，主键 `(conversation_id,user_id)`；索引 `(conversation_id,has_read_seq DESC)`。
- `group_member_limit_logs` 容量变更审计。
- `groups.max_members` 只约束 `>=3`；技术上限由部署配置负责。

## 5. 配置与发布

server 与 admin 必须设置相同配置：

```env
GROUP_MEMBER_HARD_LIMIT=4000
```

修改环境技术上限需要滚动重启 server/admin。平台上限与新群默认上限走管理后台“系统限制”草稿和发布流程；只有 `app_config_versions.status='published'` 的最新版本参与 server 判定。修改单群上限不需要重启。

## 6. UI

- 管理后台系统限制页显示只读的技术安全上限，并编辑平台上限、新群默认上限。
- 群详情抽屉内使用独立 `GroupCapacityEditor.vue` 编辑单群上限；低于现有人数时明确提示不会踢人。
- APP 群消息直接复用 `ChatBubble.vue` 的私聊 `readState` 单/双勾，不增加另一套视觉组件或文案。
- 聊天房间不再为了标题和权限一次性加载全部群成员，避免进入 4000 人群就拉取全量成员。
- 管理后台群成员列表使用服务端分页，默认每页 50 人。

## 7. 测试数据与验收

独立脚本位于 `IM-APP-server/scripts/testdata/`。测试手机号为 11 位数字；脚本经业务注册接口创建用户，再调用 `/im/token` 确认 OpenIM 已注册且能签发 token。清单保存到 `.tmp/testdata/<batch>/users.jsonl`，目录已忽略，不会把 token 提交到仓库。

```powershell
cd IM-APP-server/scripts/testdata
./prepare-im-users.ps1 -Count 20 -Batch local-read
./verify-im-users.ps1 -Manifest ../../.tmp/testdata/local-read/users.jsonl
./prepare-test-group.ps1 -Manifest ../../.tmp/testdata/local-read/users.jsonl
```

验收覆盖：3/平台上限/技术上限边界、并发加入、批量邀请原子失败、降低到现有人数以下不踢人、Redis 不可用回退 PostgreSQL、重复或倒序游标不回退、非群成员 403、任一读者读后双勾、页面隐藏停止轮询。

## 8. 回滚与观测

- 前端回滚不会破坏游标表；旧版本 APP 不上报游标，其群消息保持未读显示。
- Redis 不可用自动回退 PostgreSQL，数据库是事实源。
- 回滚容量功能时保留 `groups.max_members` 和审计表，不删除历史数据；将平台配置恢复到上一发布版本即可。
- 监控两个已读接口的 QPS/P95/错误率、OpenIM 游标查询次数、Redis 命中率、容量 409 次数和超限群数量。
