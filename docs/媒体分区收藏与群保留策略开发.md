# 媒体分区、收藏副本与群保留规则

本阶段在 `feat/chat-image-speed` 开发，仅提交代码。本次没有部署、发布 WGT、改动现有环境配置或对现有环境执行消息/对象删除；正文清理测试只在本次新建的空测试库内运行。

## 1. 交付范围

| 客户要求 | 本阶段实现 | 尚需完成 |
| --- | --- | --- |
| 头像、聊天、收藏分开 | 新 OSS 头像使用 `avatars/`；业务语音使用 `chat/voices/`；收藏复制至 `favorites/`；转发和引用副本使用 `forwards/`；OpenIM 媒体沿用已有独立聊天桶及前缀 | 发布时核对真实 OSS 地址范围；已有对象不搬迁 |
| 头像与收藏长期保存 | 本阶段不为头像、收藏设置过期或删除；新媒体收藏成功依赖独立文件复制完成 | 核对外部 OSS 生命周期没有覆盖这些目录；旧收藏须补偿后才具有独立副本 |
| 每群每日保留最近 7 天、最多 500 条 | 规则、可信尾部快照、每日任务、单调可见边界及 H5/App 水位同步已实现，默认关闭 | 完整 OpenIM 并发/积压测试、真实设备验收、OSS 文件回收；非前缀时间乱序和尾部空洞目前安全拒绝 |
| 已过期群消息正文延迟清理 | 新增独立 worker：首次 ACK 至少 24 小时后，指定群、有限批次、原子槽位 fence 和进度续跑；真实转存 controller 并发重放测试通过 | 默认关闭，仍须完整 OpenIM/手机验收；不删除 OSS 文件、不保证宿主机磁盘立即下降 |
| 单聊、收藏、跨会话转发不被源群清理损坏 | 新收藏独立保存；新客户端转发、引用和队列转发先复制媒体，复制失败停止发送；旧待投递任务在发送前补偿；源过期保留嵌入引用 | 已投递旧转发/引用和旧客户端发送的引用仍需补偿；全部有效引用、上传在途、去重映射处理完成前不能启用 OSS 文件回收 |

不能直接给聊天桶配置“创建满 7 天删除”的生命周期。对象创建时间不等于消息发送时间，同一文件也可能被新的消息或其他会话继续引用。

## 2. 存储目录与兼容

以 `OSS_KEY_PREFIX=app/business/` 为例：

```text
业务桶
  app/business/avatars/<userId>/<uuid>.<ext>
  app/business/chat/voices/<userId>/<uuid>.m4a
  app/business/favorites/<ownerId>/<messageId-hash>/<content-sha256>
  app/business/forwards/<ownerId>/<snapshot-hash>/<content-sha256>
  app/business/uploads/...                  其他现有业务上传

聊天桶
  <既有聊天前缀>/...                         OpenIM 图片、视频、语音、文件
```

前缀从配置读取，示例不是要求创建新桶。新增收藏副本属于收藏人；转发/引用副本属于发起人，接收方沿用该长期副本地址；两者都不会改写源消息。当前没有删除未引用副本的任务，失败后留下的对象也不会在此阶段自动回收。

上传请求、完成请求及响应结构保持现有契约。仅 OSS 新头像、新业务语音采用上述新目录，MinIO 旧路径和已有上传任务仍按原记录的 provider/bucket 处理。

收藏解析保留 camelCase/PascalCase、字符串内嵌 JSON、音视频元数据和大整数 ID。前端继续提交现有收藏快照，成功后才显示“已收藏”。本次另行接入转发、引用的前置副本接口和分平台 SDK 调用，详见下节；尚未完成新版本的真机验收。

### 转发和引用的独立副本

新增鉴权接口 `POST /api/v1/forward-media/preserve`，仅接收 JSON 请求体：

```json
{"sourceSnapshot":{"contentType":102,"content":{"sourcePicture":{"url":"https://chat.example.com/app/chat/image"}}}}
```

接口返回 `{contentType, content}` 快照，不发送消息。服务端按登录用户和规范化快照计算缓存键；客户端不能指定副本所有者、目录或归档标志。快照内的图片、语音、视频、文件及嵌套引用/合并消息先逐项检查完整性，再复制所有媒体，成功后才持久化结果。视频须同时有远程视频和封面；只有本地路径、缺失原文件、缺失子消息或任一复制失败都会停止本次发送。普通文字中的网址保留为文字。

源读取沿用收藏的受限地址范围和签名 URL 访问能力，包含每次跳转；不额外验证源消息存在或群成员关系，不附加用户 JWT/Cookie。接口不接受 query、额外顶层字段或超出 128 KiB 的请求体。无效快照返回 400，副本/存储故障返回不含源地址和凭据的 503；具体契约见后端 OpenAPI、Postman 集合和 `docs/api-contract.md`。

H5 与 App 的 `sendForwardMessage` / `sendQuoteMessage` 在创建 SDK 消息之前等待副本完成，失败时向上层报错，不回退到源文件。前端统一处理 camelCase/PascalCase、字符串内嵌 JSON、媒体元数据、@成员信息及嵌套引用，并复制 iOS 可能冻结的对象。H5 的 `CreateForwardMessage` 直接传消息对象，App 原生桥传 `{message}`；引用消息继续按 SDK 契约传 JSON 字符串。已经归档的媒体转发走 `SendMessageNotOss`，不重新上传本地文件。

队列任务在创建、提交及 worker 发送前共用保护逻辑，旧的未归档待投递任务会先补偿并以 CAS 冻结新快照。创建时复制失败可能留下未投递草稿，用原幂等键重试；批次失败时前面任务可能已提交，也必须用原批次幂等键重试，不能重新生成键。已成功的任务不重新添加目标或重复入队。

这些保护覆盖更新后的发送入口和未完成队列任务；不会自动重写已经投递到 OpenIM 的历史引用，也不能约束尚未更新的旧客户端。群清理和对象回收尚未启用，因此本次没有删除旧引用依赖的源文件。

## 3. 数据库迁移与上线前配置

新增四项增量迁移，均不删除消息/文件数据，测试已验证重复执行：

- `IM-APP-server/migrations/052_media_preservation.sql`：给 `favorites` 增加内部 `media_archived` 标志及待补偿媒体索引。
- `IM-APP-server/migrations/053_forward_media_preservation.sql`：给 `forward_tasks` 增加内部 `media_archived` 标志及待补偿索引，新增按所有者隔离的 `forward_media_snapshots` 副本快照缓存表。
- `IM-APP-server/migrations/054_group_retention_plans.sql`：群/UTC 日期幂等的规划队列、租约及预览计划。
- `IM-APP-server/migrations/055_group_retention_visibility.sql`：独立应用租约/ACK 及全群最小可见序号、递增版本。

旧记录默认未归档，标志不暴露到 API JSON。

新空库仍使用现有自动迁移；已有环境使用 `MIGRATIONS_MODE=verify` 时，先单独应用审核后的 052–055，再切换后端程序，确认新接口可用后更新 H5 和 App。新程序即使清理 worker 关闭，也需要 055 的 visibility 表才能提供水位查询。不能直接拿新二进制接旧表结构，也不能先更新客户端再部署接口。这里没有运行任何现有环境的迁移。

新增下载范围配置，多个值用逗号隔开：

```dotenv
MEDIA_SOURCE_URL_PREFIXES=https://chat-oss.example.com/app/chat/,https://www.example.com/object/
```

- 目录以 `/` 结尾；稳定解析端点可写精确路径，例如 `/api/v1/public/oss-media`。
- 当前业务 OSS 上传域名、公共读取域名及业务前缀、业务稳定解析端点、配置的 OpenIM 公共域名 `/object/`、旧 MinIO 公共桶路径会自动纳入。
- 聊天对象解析通常会 302 跳转至聊天 OSS 域名，**真实跳转目的域名及应用前缀也必须显式纳入**。只配置 `/object/` 不够；有效 GET 签名查询参数原样传递，不把签名 URL 写入配置。
- 仅允许配置的 HTTP(S) host/path；每次重定向也检查，不允许整域名或桶根路径，不附加 JWT/Cookie。下载只连接公网 IP，禁用系统代理并拒绝私网、回环及云元数据地址。部署在同机的旧 MinIO 也不能直接使用 `127.0.0.1` 或容器地址；需要可访问的公共受限路径，或另外设计受信任的存储适配器。
- 此配置与收藏服务共用持久化的业务 OSS 签名配置。不要轮换 `OSS_MEDIA_SIGNING_KEY` 来测试，否则旧稳定地址可能失效。

收藏、转发和引用的最大快照均为 64 KiB（包括重写结果）、最多 64 个媒体 URL、累计文件 512 MiB。归档上下文最长 45 秒，单次 HTTP 下载最长 40 秒；网络慢或文件过大时返回可重试的失败。普通客户端上传继续遵守原 20 MiB 限制。

独立副本使用消息 ID 哈希和文件 SHA256 的确定性 key，HEAD 已存在且大小一致时复用，写入禁止覆盖。只有副本完成后才写收藏记录；旧记录用 CAS 更新，并发冲突重新读取持久化结果。共享事务锁保留给将来的维护协调；它本身不意味着删除已具备引用保护。

## 4. 旧收藏补偿工具

在 `IM-APP-server` 目录运行。必须由操作者通过安全配置注入 `MEDIA_ARCHIVE_DATABASE_URL`，明确指定本次目标数据库；工具**不会回退到 `.env` 的 `DATABASE_URL`**。其余存储设置可从进程环境或该目录 `.env` 读取。不要在日志、聊天或 Git 中放数据库密码、AK/SK。

默认只读预览，不创建存储客户端，不执行迁移或种子初始化：

```shell
go run ./cmd/archive-favorites -limit 100
```

输出待处理的收藏 ID、状态及 `nextAfter`，不输出内容、源地址或凭据。旧库须已经具有 052 的字段。

在独立测试数据库验证配置后，显式使用 `-apply` 才会下载、复制并提交收藏新快照：

```shell
go run ./cmd/archive-favorites -apply -limit 100
go run ./cmd/archive-favorites -apply -after <上批最后一个收藏UUID> -limit 100
```

每次最多处理 `-limit` 条（1～10000），按 UUID 游标分页。源已失效等失败项保留原记录并计入失败数，不阻塞后续分页；有失败时进程非零退出。`nextAfter` 只表示本批扫描位置，**不表示之前失败项已完成**。要重试失败项，从头运行不带 `-after` 的命令；已经成功的记录不再进入待处理列表。

工具只更新收藏快照，不删除源消息、源对象或用户的收藏。列表查询也不会隐式执行批量迁移。当前方案不提供已失效旧链接的自动恢复。

另有 `FAVORITE_ARCHIVE_WORKER_ENABLED=false`（默认）可显式开启 OSS 旧收藏补偿。每轮最多 20 条，单条最长 50 秒；坏源不阻塞后续记录，扫完一轮等待一小时再重扫。成功进度为持久化 `media_archived`，游标仅为当次扫描位置，重启重新扫描安全。多副本通过已有事务/CAS 和确定性 key 保持幂等，不伪造失败源的成功标志、不删除源文件。

## 5. 群聊保留规则预览

`cmd/preview-group-retention` 从标准输入读取规范化完整快照，输出 `mode=preview_only`。不读 `.env`、不连接服务、没有删除或定时能力。生产可信快照由独立的私有 OpenIM v2 适配器提供，不是客户端导出的普通分页搜索。

输入样例 `snapshot.json`：

```json
{
  "conversationId": "sg_example",
  "sessionType": "group",
  "serverTime": "2026-10-18T03:00:00+08:00",
  "committedWatermark": 10,
  "complete": true,
  "messages": [
    {"seq": 1, "sendTime": "2026-10-10T03:00:00+08:00", "visibility": "visible"},
    {"seq": 7, "sendTime": "2026-10-18T02:00:00+08:00", "visibility": "visible"},
    {"seq": 8, "sendTime": "2026-10-18T02:00:01+08:00", "visibility": "hidden"},
    {"seq": 11, "sendTime": "2026-10-18T03:00:01+08:00", "visibility": "visible"}
  ]
}
```

PowerShell：

```powershell
Get-Content -Raw -Encoding utf8 snapshot.json | go run ./cmd/preview-group-retention
```

Linux：

```shell
go run ./cmd/preview-group-retention < snapshot.json
```

样例 seq=1 超过 168 小时列为候选，seq=7 保留，隐藏控制记录不计数，超过固定水位的 seq=11 留待下一批。最新 500 条按实际存在、可见消息的服务端 seq 排序计数，展示型群通知也算可见；不能用 `maxSeq-500`。刚好位于时间边界的消息保留，任一限制超出即列为候选。快照不完整、单聊、重复 seq、未知分类、可见记录无时间或时间晚于快照时拒绝生成计划。

`complete`、`serverTime`、已提交水位及可见分类是适配器的保证，并非填写 JSON 就获得服务端权威性。预览输出不能直接当作删除授权。

## 6. 已实现的自动逻辑清理链路

详细的构建、私网协议、配置、发布顺序、止损及验收见 `deploy/openim-retention/README.md`、`ACCEPTANCE.md`。本轮不再改动图片缓存实现。

### 6.1 可信尾部快照与安全边界

- 固定 OpenIM `v3.8.3-patch.15` / protocol `v0.0.73-alpha.18`；源文件 SHA256 与锚点校验后仅在一次性源码副本上应用补丁。
- 私有协议 `im-app-retention-visibility-v2`，专用 >=32 字节 key，不对公网开放，不透过 Nginx 发布。GET 快照、能力查询；POST JSON 应用收据。业务适配器拒绝重定向、禁用系统代理、响应不超过 4 MiB，不输出上游 URL/凭据。
- 固定当前水位，使用 Mongo 服务端时间；每个扫描槽位校验实际持久化内容、群身份、seq、消息类型和时间。尾部空洞/未知分类不是已提交证明，必须重试。
- 从新到旧取实际可见消息，证明 500 条后用 `overCountThrough` 概括更早的超额前缀，因此首次百万级历史也不必全量读取。隐藏控制不计数，不采用 `maxSeq-500`。纯规则复算并校验至少 500 条可见证据。
- 尾部扫描上限 20,000 个槽位；超限、安全证据不足或时间乱序导致非前缀计划时拒绝，不假报已清理。数据库 `candidate_count` 仅表示显式扫描候选，不包含概括前缀，不能当作物理删除统计。
- 收据 UUID 绑定会话、精确边界及有效期；Mongo 时间验证过期，30 天 TTL 仅清理收据元数据。客户端或旧的预览 JSON 不能伪造授权。
- 应用仅单调推进 OpenIM 全局 `min_seq`，Mongo `$max` 防回退；同时修复原分配器反复 `$set min_seq=0` 的问题。**发布必须更新消息 RPC 和全部消息转存进程**，只更新 RPC 会被旧转存 allocator 重置水位。
- 历史拉取原有范围控制沿用；补齐服务端搜索（分页/计数前过滤）、定位和最后消息过滤，返回的已读序号至少为过期前缀末尾且不回退用户已读值。不把剩余有效消息一并标为已读。

### 6.2 每日持久化队列与应用 ACK

- 054 以业务群 UUID + 数据库 UTC 日期为唯一键，每日有效群幂等入队，每轮最多 2,000 群。规划 `queued → planning → planned`，失败退避 `retry`，8 次后 `blocked`。
- 规划与应用均使用 2 分钟租约、随机 token + 到期 CAS；过期可接管，旧 worker 不能提交结果，第 8 次崩溃后的死租约也能转阻塞。
- 055 应用队列独立记录 `queued → applying → applied`。可信适配器持久化 ACK 后，在同一 SQL 事务中提交应用状态和单调可见边界/版本。只生成 `planned` 不发布清理水位。
- worker 每分钟串行、每轮最多 20 次规划/应用；一个群的历史异常进入自己的退避，继续处理其他群；私有协议/认证能力失败则在领取前停止。
- `GROUP_RETENTION_MODE=off` 默认关闭；`queue_only` 仅入队；`visibility_only` 显式要求私有桥 URL/key 并执行逻辑清理。没有物理删除模式，`apply`、`cleanup`、`true` 等拒绝启动。
- `visibility_only` 还必须显式提供 `GROUP_RETENTION_GROUP_IDS`（最多 100 个唯一规范业务 UUID）或 `GROUP_RETENTION_ALL_GROUPS=true`；不能混用/隐式全群。名单同时限制入队、规划领取、旧计划回填、应用领取。初次用一个专用群灰度，缩小范围不删除既有客户端水位。
- 日任务元数据目前不自动归档，长期启用需规划增长；可见边界不能按 LRU/日期删除。

### 6.3 客户端同步

新增鉴权只读 `GET /api/v1/im/group-retention/states?conversationIds=sg_<32hex>,...`，一次 1–50 个规范且唯一的群会话 ID。GET 无 body，只接受这一 query 字段；在 SQL 查询内部验证有效用户、有效群及当前群成员身份。仅返回实际应用后的 `{conversationId,minVisibleSeq,revision,updatedAt}`，`private,no-store`；没有写/删除权限。

H5 和 App 共用每账号持久化水位，兼容冻结对象和 PascalCase/字符串 seq。历史、搜索、定位、实时消息、发送 ACK、本地消息列表和会话摘要均按水位过滤；SDK 已读/未读同步前对过期前缀做保守上限修正，不清空剩余有效未读。会话摘要的消息 ID/seq 与文案一并更新，原生延迟 seq 回执只更新自己的摘要；清历史/切号后不能通过旧回执重新插入消息或原始快照。30 秒轮询及重连/重新拉取对齐在线状态。切号请求有 generation fence，空响应、失败、旧版本响应不降低已有边界；退出登录/清业务缓存不丢 tombstone，超过 5,000 群也不静默丢弃旧状态。

这不意味着删除 SDK 原生数据库或离线数据。设备离线只能遵守已知水位；首次同步失败、永久旧版本仍有局限，需要在线同步和真机验收。收藏/嵌套引用展示不因源群历史不可见而被一并隐藏。

### 6.4 明确未完成：OSS 文件回收和完整真机验收

默认配置仍保留 Mongo 原消息；新增正文 worker 见 6.5，需单独开启。**旧 MinIO 文件、OSS 原对象及 OpenIM 文件映射始终保留，不释放 OSS 源文件空间**。保留原文件保护历史已投递引用和旧客户端，不等于已完成历史引用独立归档。OSS 回收仍缺跨会话完整引用、历史引用补偿、上传在途保护及 OpenIM 去重映射协调，不能启用桶根 7 天生命周期或直接裸删。

非前缀时间乱序、尾部空洞/超多隐藏控制目前安全拒绝；完整 OpenIM 并发/积压与 iPhone/Android 尚未验收。**因此不能宣布全部客户要求完成，也不能自动开启生产清理。** 本地增量包构建器只构建业务 API、消息 RPC、转存二进制、052–055 和校验清单，不上传密钥、不发布 H5/WGT、不重启服务；现有 OSS 切换 bundle 不适用本次发布。

### 6.5 新增：默认关闭的 Mongo 正文延迟清理

具体配置、观察和止损见 `deploy/openim-retention/BODY-PURGE.md`。正文清理独立于业务逻辑 worker，必须显式选择 1–100 个 OpenIM 群 ID 并由操作者确认全部读写进程与客户端门禁；默认关闭，不支持隐式全群。

- 私有逻辑 ACK 成功后用 Mongo 时间记录首次 `applied_at`，重试不延长缓冲；至少等待 24 小时，按名单再核验持久化 `min_seq`。
- 每分钟最多 5 个收据，每收据最多 10 个 100 槽位文档；最后尝试时间轮转避免失败群饿死其他群。逐文档成功才单调记录进度，重启有限续跑。
- 原子清空过期槽位并在同文档推进 fence；保留文档骨架和有效尾部，不用 `$pull`。缺失文档也建立骨架，防止迟到的首次转存重新创建旧正文。
- 真实转存 controller、消息 RPC controller 的写入均遵守 fence，过期重放成功但无改动，不陷入重复键死循环；管理销毁路径不丢 fence。
- 引用源低于清理边界时保留内嵌快照，不把缺源误判为撤回。没有对象存储依赖，不删除头像、收藏、转发副本、单聊或 OSS/MinIO 原文件。
- `capabilities` 额外报告 `bodyPurge=off|mongo_bodies_only`、`objectPurge=off`。默认覆盖层仍关闭正文清理；发布清单明确 `mongoBodyPurge=disabled_by_default`、`ossObjectPurge=false`。

这只实现 Mongo 正文清理，不表示 OSS 图片已回收，也不保证宿主机磁盘立刻下降。未部署/未完成完整服务及手机验收。启用后不能回滚到不认识 fence 的旧写入进程；关闭业务逻辑 worker 不会停止已 ACK 的正文待办，须另行关闭正文开关并清空 scope/ACK。
