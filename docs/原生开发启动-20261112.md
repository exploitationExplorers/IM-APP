开发分支：`codex/native-bootstrap`。现有 uni-app 与原生工程在同一仓库并存；本次未提交或发布任何线上变更。

- `IM-APP-android/`：Kotlin + Compose，测试包身份独立于现网 App。
- `IM-APP-ios/`：UIKit App + `Packages/IMCore`，Swift Package 无外部依赖。

用户已确认当前没有独立测试环境与 Mac，因此先推进本地代码和测试。原生工程依赖、临时数据和模拟器工作数据写入仓库下 D 盘的 `.native-cache/`，该目录不入库；REA 研究工具与证据使用 D 盘 `.analysis/native-rea-recovery-20261112/` 独立目录。所有新增下载保持在 D 盘，已有 Android SDK 和 JDK 继续复用。

## 本轮功能边界

双端 API adapter 对接现有的密码登录、短信登录、验证码申请、Token 刷新、IM Token 五个 POST JSON 接口，以及 `GET /me`。用户已授权先用现有后端：普通登录默认连接 `https://www.xn--jprz53bj9s.com/api/v1`（现有 `www.易可聊.com` 的 ASCII 域名），无需长按 Logo 配置。保留 HTTPS 与证书验证，不使用旧 `.env` 的明文 HTTP 地址。

业务用户 ID 与 IM 用户 ID 分离。会话 ticket 同时包含账号与 generation；每次同步另有 attempt 标识，旧账号、旧登录和旧同步的回调都不得推进新状态。同步失败或超时不能变成完成，也不能自动清库。

正常密码登录顺序为 `POST /auth/login` → 携带 `Authorization: Bearer accessToken` 的 `GET /me`；`/me` 的 `data` 直接是用户资料。成功后进入真实账号主页，“我的”显示本次登录账号的昵称、账号及脱敏手机号。资料请求失败时使用本次登录响应的真实 `user` 并提示；资料 ID 冲突不会接收另一账号：Android 回退登录资料并提示，iOS 拒绝进入。退出清除内存凭据并隔离迟到结果；当前未做持久登录，进程重启后需重新登录。

业务登录不请求 IM Token：现有后端源码提示重新签发 IM Token 可能使先前凭据失效，尚无 SDK 时不做多余签发。本地样例只验证导航、文本列表和输入，明确标注不联网、不送达；真实账号主页不混入样例会话，聊天与通讯录显示接入中。OpenIM SDK 的兼容版本、开库、同步和迁移仍需后续接入验证。

## 本地检查

在仓库根目录执行：

```powershell
python -X utf8 scripts/native/verify_contracts.py
python -X utf8 scripts/native/verify_bootstrap.py --require-baseline --output .native-cache/verification/bootstrap.json
& ./IM-APP-android/build.ps1 -Offline
```

无初始缓存的新机器需先联网解析依赖，去掉 `-Offline`。Android 构建环境和完整命令以工程 README 为准。API 34 是复用现有离线工具的原型基线，不代表已经满足正式商店发布要求。

有 Mac 后执行：

```bash
swift test --package-path IM-APP-ios/Packages/IMCore
xcodebuild -list -project IM-APP-ios/IMNative.xcodeproj
xcodebuild -project IM-APP-ios/IMNative.xcodeproj -scheme IMNative -sdk iphonesimulator -configuration Debug CODE_SIGNING_ALLOWED=NO build
```

Windows 无法执行以上 Swift / Xcode 检查。CI 文件已经提供对应 Mac job，但配置存在不等于远程运行通过。

## 对线上用户的影响与后续后端规则

本阶段复用现有接口，不改 Go 后端、数据库结构、OpenIM 服务配置或线上部署。本次登录修复已核对 539 份旧后端 / 前端文件与本轮开始基线一致。旧前端此前已有的并行修改不回退、不覆盖，也不计入本轮登录修复。

后续确需改后端时遵守以下发布约束：

1. 旧 App / H5 继续使用原有请求与响应语义。优先新增静态路径接口或可选字段；不直接改变字段类型、用户 ID 映射、消息状态与已读规则。
2. 数据迁移先扩展后收缩；新旧版本共存期间不删除或重命名旧列，不直接强制升级所有客户端。迁移在测试库检查时长、锁影响与恢复方案。
3. 新原生能力默认关闭或只对测试账号开放；保持旧客户端路径可用，先发兼容后端，再发客户端，验证后分批开放。
4. 发布前回归旧 App、H5 和新原生端的登录、互踢策略、聊天、媒体、已读与群规则；同时核查请求量、错误率及数据库负载。
5. 出现异常先停放量或关闭新能力。数据库迁移不能仅靠回滚旧二进制恢复，应另验证兼容修复和数据恢复策略。

这些约束用于降低风险，不能在未测试、未发布验证前承诺任何未来后端修改绝对零影响。正式应用身份、签名与旧库迁移没有验证前，生产构建保持阻止状态。
