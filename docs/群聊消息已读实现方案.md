# 群聊消息已读(读回执)实现方案

> 项目:IM-APP(uni-app 前端 + Go 后端 + OpenIM 私有化 `v3.8.3-patch.16`)
> 状态:方案设计 · 调研结论已由源码/已装 SDK 核实
> 日期:2026-08-19

---

## 一、需求

群聊中,用户**发送**一条消息后,能看到**自己这条消息是否被已读**。

- "随便一个人看了都算已读" → 每个群成员只要打开会话看到这条消息,就计为该成员"已读"。
- 发送者能看到聚合结果:已读人数 / 未读人数(以及可选:已读成员列表)。

产品形态对齐微信:发送者在自己的群消息气泡下方显示"已读 x/y"。

---

## 二、结论(先给结论)

**OpenIM 社区版 v3.8.3 不直接提供"谁读了我的群消息",需要后端(GO 服务)改造来实现。**

但不必自研消息存储或已读表——**OpenIM 社区版本身就在维护每个用户在每个会话上的"已读游标 `hasReadSeq`"**(会话未读数 `unreadCount` 就是基于它算的,项目前端一直在上报)。我们的方案是:

> **后端读取群内每个成员的 `hasReadSeq`,若 `成员.hasReadSeq >= 消息.seq`,则该成员已读这条消息。**
> 前端(发送者)调后端查询接口,展示"已读 x/y"。

OpenIM 侧无需改代码,只需 Go 后端新增查询接口;前端新增查询 + UI 展示。

---

## 三、调研结论(为什么"白嫖"不了 OpenIM 现成能力)

### 3.1 OpenIM 原生已读能力现状

| 能力 | 单聊 | 群聊 | 说明 |
|---|---|---|---|
| 消息 `isRead` 字段 | ✅ | ❌ | 单聊消息上直接带已读标记 |
| 已读回执事件推给发送者 | ✅ `OnRecvC2CReadReceipt` | ⚠️ | 见下方"重要发现" |
| 查询"谁读了某条群消息" | — | ❌ 社区版 | `getGroupMessageReaderList` 仅企业版/文档提及 |
| 会话级未读数 `unreadCount` | ✅ | ✅ | 基于每人 `hasReadSeq` 计算,可靠 |
| 群已读 webhook | — | ⚠️ 有但字段不全 | 见下方 |

### 3.2 重要发现(已核实)

1. **`getGroupMessageReaderList`(查已读成员)在已装社区 SDK 中不存在。**
   已安装的 `@openim/client-sdk@3.8.3-hotfix.0` 运行时 bundle 里没有 `getGroupMessageReaderList`、`sendGroupMessageReadReceipt`、`readMembers` 字段,只有事件名枚举。该能力在 OpenIM 官方文档中标注为 **商业高级版支持**(`GroupHasReadInfo` / `hasReadUserIDList`)。

2. **社区版服务端不会把群已读回执推给"其他消息发送者"。**
   从 `open-im-server v3.8.3-patch.16` 源码 `internal/rpc/msg/as_read.go` 的 `MarkConversationAsRead` 看,群会话已读时只:
   - 更新读者自己的 `hasReadSeq`;
   - 给**读者自己**发一条已读自回执(`MarkAsReadTips`);
   - 触发 `afterGroupMsgRead` webhook。
   并不会把"谁读了"推给群里的其他发送者。

3. **`afterGroupMsgRead` webhook 存在,但 payload 不含会话/群 ID。**
   `config/webhooks.yml:115` 有 `afterGroupMsgRead`,默认 `enable: false`。
   回调结构体 `CallbackGroupMsgReadReq`(源码 `pkg/callbackstruct/message.go:83`)只有 `{ callbackCommand, sendID, receiveID, unreadMsgNum, contentType }`,且构造时 `sendID = receiveID = 读者 userID`,`unreadMsgNum = hasReadSeq`。→ **后端收到后无法直接知道读者读的是哪个群**,不能作为主链路,只能作为"有人已读"的弱信号。

### 3.3 所以

社区版可靠可用的只有"每人每会话的 `hasReadSeq`"。用它 + 消息的 `seq`,即可精确算出一条群消息被哪些成员读过。这就是本方案的基础,且**全部在 Go 后端可控范围内**,不需要动 OpenIM 镜像或改群消息存储。

## 四、总体方案与数据流

```
发送者 App                     Go 后端(IM-APP-server)              OpenIM(私有化)
   │ 发送消息(OpenIM SDK) ──────────────────────────▶  msg.send_msg (seq 已定)
   │
   │ 进入会话 / 发送后 / 定时
   │ GET /im/messages/read-status?conversationID&seq ─▶ ① 校验发送者是群成员
   │                                                 ② 取群成员列表(admin)
   │                                                 ③ 并行取每人 hasReadSeq(admin)
   │                                                 ④ hasReadSeq>=seq → 已读
   │ ◀── { hasReadCount, unreadCount, readMembers }  ⑤ Redis 缓存 ~5~10s
   │
   │ 气泡下显示 "已读 3/5" / 点开看已读成员
```

- 权威数据源:**OpenIM 每成员的 `hasReadSeq`**(而非自建已读表)。
- 后端只读不写 OpenIM;新增一个查询接口。
- 前端轮询(聊天页打开时 ~5s)+ 关键时机刷新,即可做到准实时。

## 五、后端改造清单(含 OpenIM 服务器侧)

### 5.1 OpenIM 侧(服务器)

- **主链路不需要改 OpenIM 配置**(读 `hasReadSeq` 走 admin REST 即可)。
- (可选,不建议用于主链路)若要"有人刚已读"的信号,可在 OpenIM 内挂载自定义 `webhooks.yml` 把 `afterGroupMsgRead.enable` 设为 `true`。**注意**:v3.8.3 该回调不含群 ID,后端收到后只能触发一次模糊刷新,收益有限,且需注意 `IMENV_CALLBACK_URL` 已指向本后端 `/internal/openim/webhooks/:secret/`。

### 5.2 Go 后端新增(核心)

**1) OpenIM 客户端方法** —— `IM-APP-server/internal/im/client.go`

新增 admin 方法(仿照现有 `postWithAdmin`):

```
func (c *Client) GetConversationHasReadSeq(ctx, userID, conversationID string) (hasReadSeq int64, err error)
    → POST {OPENIM_API_URL}/msg/get_conversations_has_read_and_max_seq
        body: { userID, conversationIDs: [conversationID] }
    → 解析 data.seqs[conversationID].hasReadSeq;缺省视为 0(未读)
```

> 已核实该 REST 端点存在于社区版 `internal/api/msg.go:128` `GetConversationsHasReadAndMaxSeq`。

**2) 查询接口(handler + service + 路由)**

- 路由:`IM-APP-server/cmd/server/main.go` 的 `auth` 组(现有 `im/messages/recall` 附近)新增:
  ```
  auth.POST("/im/messages/read-status", imH.MessageReadStatus)
  ```
- Handler:`IM-APP-server/internal/handler/im.go` 新增 `MessageReadStatus`,入参:
  ```
  { conversationID: "sg_<imGroupId>", seq: 123 }   // 支持传多条则用数组
  ```
- Service 逻辑:
  1. 从 JWT 取发送者业务用户 → 转 OpenIM userID;校验其属于该群(`sg_` 前缀解析群 ID,复用现有群成员校验)。
  2. 取群成员 OpenIM ID 列表(复用 `im/client.go` 现有 `ListGroupMemberIDs`)。
  3. 并发调用 `GetConversationHasReadSeq`(控制并发,如信号量 10)取每人 `hasReadSeq`。
  4. `已读成员 = { m ∈ 群成员 | m.hasReadSeq >= seq }`(剔除发送者本人,见 §7 产品口径)。
  5. 返回:
     ```
     { groupMemberCount, hasReadCount, unreadCount,
       readMembers:   [OpenIM userID…], unreadMembers: [OpenIM userID…],
       readAt: 最早已读时间(可选) }
     ```
- 缓存:`im:read:sg_xxx:<seq> → 结果`(Redis,TTL 5~10s);成员游标按 `(conversationID,userID)` 缓存 TTL 更短(如 3s)。读多写少、单调递增,缓存安全。

**3) (可选)消息 seq 兜底**

前端会直接传 `seq`(见 §6)。如需服务端按 `clientMsgID` 反查 seq,可用现有审计表 `im_message_audit`(`internal/repository/im_access.go` 的 `FindMessageAudit` 已按 `conversationID + clientMsgID` 查询)。

**4) 数据库**

- **主方案无需新表**(读 OpenIM 游标,Redis 缓存)。
- (可选优化,见 §5.4 方案 B)新增 `im_group_read_cursor(conversation_id, user_im_id, has_read_seq, updated_at)`,由读者自报,做近实时与 OpenIM 对账。

### 5.3 性能与并发

- 一次查询 = 1 + N 次 OpenIM admin 调用(N = 群成员数)。本项目群为中小群,可接受;用并发 + Redis 缓存摊薄。
- 只对**发送者自己发送的最近 N 条消息**查询,不做全会话。

### 5.4 (可选)方案 B:读者自报游标,做近实时

若希望"别人刚打开我就变已读",可在读者端 `markAsRead` 成功后多调一个后端接口:

```
POST /im/messages/read  { conversationID, seq }   // 读者已读至 seq
```

后端把 `(conversationID, userID) → max(seq)` 写入 Redis/PG,发送者查询优先读本地库(毫秒级),再定时与 OpenIM 对账补漏。**优点**:不频繁打 OpenIM、可近实时; **代价**:多一套状态 + 对账逻辑,且依赖读者端是"新版本"。MVP 建议先做方案 A,上线稳定后再叠加。

- `IM-APP-fronend/src/utils/openim.ts` `toChatMessage` 透传 `seq: item.seq`。

### 6.2 API 层

- `IM-APP-fronend/src/api/im.ts` 新增:
  ```ts
  fetchMessageReadStatus(conversationId: string, seqs: number[]): Promise<Record<string, ReadStatus>>
  ```

### 6.3 Store(`IM-APP-fronend/src/stores/chat.ts`)

- 新增 `readStatusMap: Map<messageId, { hasReadCount, unreadCount, readMembers }>`。
- 新函数 `refreshOwnReadStatus(conversationId)`:取当前会话里"自己发送的、seq 存在的"消息,调 API 批量刷新。
- 触发时机:
  1. 进入会话加载历史后;
  2. 自己发送成功(`sendWithPlaceholder` 成功后);
  3. **轮询**:聊天页 onShow 时起一个 `setInterval`(约 5s)调 `refreshOwnReadStatus`,页面 onHide 清除。只查最近 20 条自己发的消息。
  4. 收到 `OnConversationChanged` / `OnRecvNewMessage` 时顺带刷一次(可选)。

### 6.4 气泡 UI(`IM-APP-fronend/src/pages/chat/index.vue`)

- 群聊 + 自己发送的消息气泡,底部显示 **"已读 x/y"**(x=已读人数,y=应读总人数,均不含自己;见 §7)。
- (可选)点击已读文案,弹出底部面板展示已读/未读成员头像昵称:
  - 后端返回 OpenIM userID,前端用 `businessUserIdFromIM()`(`src/utils/openim.ts:69`)还原业务 UUID,再经群成员数据查昵称/头像。
- 气泡对齐:未读完全部显示灰色文案,有人已读后变强调色 + 数字。

## 七、产品口径与边界(实现前需确认)

1. **"已读"的判定**:成员打开群会话(或在线收到消息时)客户端调 `markConversationMessageAsRead`,OpenIM 将其 `hasReadSeq` 推进到当时的 maxSeq。所以**"已读" = 读到该 seq 为止**,不是"点开看了这一条"。
2. **计数是否含发送者本人**:建议"已读数/总数"都**排除发送者**(对齐微信"已读 3/4"指其他人)。请产品确认。
3. **发送后才入群的成员**:不应计入"未读"。OpenIM 的 `hasReadSeq` 不含入群时间,后端需要群成员加入时间(现有 `group_members` 表/OpenIM member list 有 joinTime)来排除 seq 之后才入群的人。MVP 可先不处理并记录为已知边界。
4. **退群成员**:不计入已读/未读(取当前成员列表即可)。
5. **实时性**:社区版无实时推送 → 前端轮询 5s,体验上接近实时。追求秒级可上 §5.4 方案 B。
6. **单聊已读**:OpenIM 原生支持,前端只需订阅 `OnRecvC2CReadReceipt` + 用 `isRead` 字段即可,可顺手做(与本需求同屏)。

## 八、验收用例

| # | 场景 | 期望 |
|---|---|---|
| 1 | A 在群发消息 → 自己看 | 显示"已读 0/n" |
| 2 | B 打开该群会话看到消息 | 5s 内 A 端变为"已读 1/n" |
| 3 | C、D 也打开 | 计数递增到 3/n |
| 4 | A 重新进会话 | 已读状态立即恢复(缓存/重新查询) |
| 5 | A 发消息后立即关闭页面再打开 | 正确展示(非实时无事件,按查询结果) |
| 6 | 新成员 E 入群(晚于消息 seq) | E 不计入未读(若实现边界规则) |
| 7 | F 退群 | F 从计数中消失 |
| 8 | 群内 50 人 | 查询接口 <1s(缓存命中时) |
