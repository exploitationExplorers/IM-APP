历史聊天图片性能与流量优化方案

日期：2026-11-13。适用范围：现有 uni-app、已交付 Android 原生测试版，以及后续 iOS 原生版。本文是基于本地源码与竞品 APK 静态分析制定的实施方案；尚未采集用户慢图的真实网络与性能数据。

1. 建议与本次问题

实施更新：用户已同意按本方案开发，本轮已落地 Android 历史图片媒体层与 iOS 缓存身份等配套代码；具体交付、验证边界和仍需 Mac／真实样本完成的阶段，见本轮实施与验证。以下调查结论中的“当前 Android”特指原先交付的 0.3.0-parity，不能混同为优化后的实现。

建议保留 OpenIM 消息内核，优先重做应用自己的媒体加载与缓存层，形成统一的 IMKit。第一目标是解决“打开历史聊天，旧图片显示慢”；第二目标是减少同一资源的重复下载及 CDN／OSS 流量。当前证据不足以支持从零自研整套 IM SDK。

原生能够减少桥接和界面开销，但不会自动解决图片缓存键不稳定、离屏请求占队列、旧消息没有有效缩略图或存储交付慢。要达到接近参考软件的体验，需要把这条链路做完整，并在同设备、同网络、相同缓存状态下验收。

用户新增的聊天截图提出：“对方图片每个只下载一次，我们每次打开重新下载，CDN 和 OSS 流量大。”这提供了很明确的验证方向，但属于使用反馈，尚不是网络抓包证明。方案会直接验证第二次打开的图片响应体字节数，而不是只凭肉眼判断。

本次不修改业务后端、旧 uni-app 或线上部署；UI 和功能继续以原 uni-app 为基准。优化方案不要求改聊天外观。

2. “只下载一次”、本地缓存、CDN 与 OSS 的关系

“只下载一次”应定义为：同一账号与授权范围、同一资源版本、同一图片规格，在本地有效缓存未被清除或淘汰时，再次打开不重新传输该图片的响应体。它不是永久保存所有图片的承诺；系统清理、用户清缓存、重装、缓存容量淘汰、切换原图规格或资源更新后，可能需要重新下载。

层级作用命中后仍可能产生什么流量
手机内存缓存直接显示解码后的图片通常无需图片网络请求
手机磁盘缓存重启后仍可读取图片文件有效且授权允许时可避免图片响应体下载；必要的权限校验另计
HTTP 条件缓存服务端验证文件是否变化304 仍有请求和响应头，但没有整图响应体
CDN 边缘缓存就近分发，减少 OSS 回源用户重新下载仍产生 CDN 下行流量及请求；具体账单按厂商计费
OSS／对象存储保存原图与派生图片，承担未命中回源CDN 命中可减少回源；直连下载则仍从对象存储取图

因此，购买 CDN 无法替代手机本地缓存；仅修手机缓存也不能保证首次打开很快。客户端负责减少重复传输，缩略图减少每次传输字节，CDN 优化第一次下载和跨设备访问。

本项目确实包含 OSS 集成与 CDN 地址配置能力。是否已在生产生效、缓存命中率多少，不能从仓库配置模板得出。

参考 APK 已确认把独立上传／下载域名配置交给 OpenIM，并在图片加载前调用 resolveFileURL。打包的备用下载域名是 static.fitd5c.com，上传域名是 upload.fitd5c.com；它们是 fallback 配置，不代表已观察到实际启用。另有阿里云 OSS 地址承载备用域名配置文件，不能据此认定聊天图片就存在该 OSS。仅凭下载域名也不能确认 CDN；没有实际响应与路由证据时，CDN 厂商、命中率和聊天对象存储归属仍未知。详见存储与 CDN 审计。

5. 当前原生版确实存在的优化缺口

以下为源码观察，不等同于已确认用户设备上的主因。详细 file:line 见当前链路审计。

代码事实可能造成的体验／流量问题对应改进
MediaLoader.kt:25/30/76 用完整输入 URL 的 SHA-256 作磁盘 key部分直签 URL 的签名或参数顺序变化，会把同一资源当成新图使用受控、稳定、隔离的资源身份，下载仍使用有效授权 URL
稳定 /object/、oss-media 入口也有缓存这类入口的最终 302 签名轮换不会改变原输入 key不能笼统认定每次打开全部缓存失效，必须按 URL 类型验证
MediaLoader.kt:20/35 所有媒体共用 3 槽，缺少当前可见优先级离屏大图、头像或文件可能挤占当前聊天图可见请求优先，大文件与预取限流，按实测调并发
阻塞下载未在协程取消时立即关闭连接与读流切会话或快速滑动后，旧任务继续占用资源生命周期取消传递至网络 Call，释放连接与槽位
每张图完成后扫描并排序整个缓存目录文件多时增加维护开销索引记录大小与访问时间，后台批量清理
组件重新启动时先清空 visual 再查缓存即使命中也可能短暂出现占位内存命中直接出图，避免无意义清空与闪烁
完整文件下载后才解码；下采样只影响本地解码若实际收到大图，缩小 ImageView 并不会减少网络字节确认真正的小规格响应，预览／原图按需下载
stripe 锁覆盖下载，且解码缺少完整同资源合并不同资源可能碰撞串行，相同资源可能重复解码按精确资源 key 合并在途请求与解码任务

Android 已有 24 MiB 内存缓存、384 MiB 磁盘容量控制、RGB565 和下采样；不能描述为“完全没有缓存”。图片消息也已兼容 camelCase／PascalCase，并优先 snapshot。当前最需要补齐的是缓存身份、调度、取消和实际缩图交付验证。

首次安装的新原生 App 无法直接使用旧 uni-app 私有目录中的缓存。因此“旧版已看过的图”在新原生端第一次打开，仍可能是冷缓存。必须再打开第二次、重启后打开、断网打开，才能判断是否持久缓存失效。

6. 一次复现就应记录清楚的链路

打开会话
  → 必要的群历史可见边界校验
  → OpenIM 本地历史查询 → 消息映射 → 列表出现
  → 可见图片资源身份解析
  → 内存命中／磁盘命中／进入下载队列
  → 可信地址解析与重定向 → 首字节 → 响应体完成
  → 写缓存 → 解码 → 图片像素显示

为每张可见图片记录资源 key 的不可逆摘要、规格、缓存层、队列等待、重定向次数、首字节时间、响应体字节、实际图片尺寸、解码时间、首帧时间与取消原因。URL 只记录受控类别和脱敏 host，不记录签名、Token、私人消息或原始完整路径。

历史查询耗时与图片出图耗时分开：消息还没出现，重点查 SDK／消息映射／必要业务边界；文字已经出现但图片仍占位，重点查媒体缓存、下载与解码。当前代码没有“必须等全量同步完成才能读已有历史”的硬门槛；群 retention 与 purge 属于可见性约束，不为提速绕过。

针对截图中的“重复下载”，固定选择 20 张旧图片，记录三轮：首次打开、退出重进、杀进程后重开。每轮都统计图片响应体字节、网络请求数、内存／磁盘命中率和出图耗时。302 授权请求、304 校验和整张图片 200 响应必须分开计数；仅看请求次数会误判。

没有合适账号与真实慢图样本时，先做本地受控图片服务复现：同一内容轮换签名、参数顺序变化、稳定入口 302 变化、大图与小图、慢响应、缓存满和取消。它能验证客户端机制，但不能替代生产链路定位。

7. 推荐实现：保留消息内核，建设统一媒体层

Android 建议采用 Coil + OkHttp，接入现有 Compose；实施时固定经过兼容验证的版本，并保留静态图、GIF 与视频封面能力。也可以采用 Glide，但不同时维护两套互相独立的图片缓存。iOS 建议采用 SDWebImage + URLSession 对应能力，接口语义与缓存身份规则保持一致；实际版本、后台行为和真机性能需在 Mac 上验证。

共享的是资源模型与行为合同，不是跨平台共享一个图片数据库。各平台使用自己的可靠加载库，业务通过统一 MediaRepository 请求资源。

设计项具体要求
稳定身份环境 + 账号/授权作用域 + 存储来源 + objectID + 内容版本 + 规格；不得只以文件名作为 key
授权地址资源身份与下载 URL 分离；签名刷新不改变可信对象身份，网络请求仍必须带有效授权
未知 URL不全局删除签名或鉴权参数；不能确认资源身份的外域地址保持保守策略
缓存规格列表、预览、原图区分；同一图的不同清晰度允许分别缓存；不能用模糊缩略图冒充原图
冷／暖缓存内存直接显示；磁盘异步读取并按显示尺寸解码；下载成功原子写入，失败不留下可命中的半文件
在途合并同账号、同资源、同规格的请求共享工作；一个消费者离屏不误取消仍可见的消费者
调度先屏内，再少量邻屏；远处历史不预下载；换会话取消无消费者任务；头像与大文件不饿死聊天列表
容量维护有界磁盘缓存、增量索引、后台清理；不要每下载一张图都全目录扫描
可见性切号隔离；退出、权限变化、群历史清理按既有政策清除索引与内容；缓存不能绕过消息可见规则
诊断通过功能开关和采样输出阶段指标，不输出用户内容；可回退旧加载器便于对比

不要照搬“缓存 key 一律删 Token”的做法。业务 token 可能代表不同对象或权限；只有能从可信消息／服务端映射得到稳定对象身份时，才将身份与授权分离。现有旧端的规范化经验可以借鉴，但必须保留账号与环境隔离。

8. 真缩略图、旧消息与服务端兼容

现有业务 oss-media 已有列表 360px、quality 60、WebP，以及移动预览 960px 的规格实现。客户端写了 width=360，并不代表生产最终响应已经缩小；/object/ 属于 OpenIM 对象服务，不能把业务 oss-media 的实现套给它。

第一步按实际慢图来源抽样验证：snapshot 是否缺失或等于原图、最终 MIME／字节数／宽高、服务是否识别处理参数、是否经历多个重定向、是否实际 CDN 命中。GIF 单独制定首帧／动画策略，不能把动画全部变成静态图导致功能退化。

若真实样本证实旧路径无法出缩略图，再新增受控兼容解析：只接受已验证存储来源和对象 key，校验现有访问范围，按规格白名单生成派生图，必要时后台按需补图。同一内容版本的同一规格复用结果，失败可回退合法原地址。不要在打开会话时同步扫描和转换全部历史图片。

旧消息与旧客户端保持兼容：不批量改写线上消息内容，不删原图，不改变现有接口字段语义；新能力使用可选字段或新接口，通过开关只对测试客户端启用。先验证再灰度，保留回退路径。线上风险可控制，但未实测前不能承诺任何后端改动绝对无影响。

storage_media.go 的 private,no-store 针对临时签名 302；不要为了提速把过期 Location 公开长缓存。对象内容的缓存、派生图 key 和 CDN 策略独立配置；私有图片不能因此变公开。CDN 缓存键需与签名验证、规格和资源版本共同设计，不盲目忽略全部 query。

流量核算至少区分：App 图片下行字节、CDN 下行字节、CDN 回源字节、OSS 直连与回源字节、缩略图处理和请求次数。各指标来自对应端，不能把客户端统计直接当作供应商账单。

9. 发送图片的单独优化

本次用户已明确主场景是历史旧图，但发送链路也有缺口：当前 Android 图片阶段主要做文件拷贝和尺寸读取，未做常规静图压缩；上传完成后才创建媒体消息并显示，发送者也可能再按远程地址取图。它们不能解释所有历史图片慢，但值得下一阶段处理。

建议流程：选图 → 持久化媒体任务与本地预览 → 显示明确的上传中气泡 → 后台生成列表缩略图及合理压缩图 → 上传 → 使用稳定唯一标识创建 SDK 消息并提交 Outbox → 发送／确认。上传前的本地任务不能伪装为 SDK 已发送消息；回调要防切号、防重复提交，进程恢复后继续可追踪。

列表优先本地文件，远程地址作为跨端资源；点击原图才下载原图。保留“原图”选项，GIF 不按静图压缩，处理 EXIF 方向和系统照片权限。发送状态不明时先查证，不盲目重发产生重复消息。

10. 是否需要自研 SDK

路线适用条件本次建议
自有 IMKit／媒体层 + 现有 OpenIM coreUI、缓存、调度、压缩、资源兼容、发送本地回显等问题现在做，最贴合已确认缺口
官方 SDK 升级或定点 fork有可复现的 SDK 查询、同步、事务或回调缺陷，并验证服务协议兼容依据 trace 与回归结果决定
从零自研完整 IM 内核长期愿意承担协议、ACK、顺序、去重、重试、多端同步、数据库迁移、推送及持续兼容当前不建议，不能直接解决图片重复 HTTP 下载

REA 已确认参考软件直接使用 OpenIM 消息查询，随包版本与 Go build info 显示定制 fork。它说明对方在 OpenIM 基础上做工程化，不说明必须复制其 fork，更不说明其 fork 可直接接我们现有服务。没有 fork 源码差异与互通测试，不能直接替换。

SDK 治理继续遵守原方案：SDK 独占消息数据库；App 自有库只管理草稿、Outbox、媒体任务和索引；账号、环境与登录代次隔离；不自动删库“修同步”；不移除 retention／purge；不把应用缓存优化扩大为修改 SDK 内部 checkpoint。

以下为拟定目标，尚未实测达标。完成基线后确认设备、样本和阈值，保留失败样本与原始记录。

场景条件与目标
内存暖缓存固定样本、页面可见开始到像素显示，P95 目标 ≤100ms；不重复传输图像响应体
磁盘暖缓存杀进程重开，缓存仍在且账号／权限有效，P95 目标 ≤250ms；同规格图片响应体字节为 0

真实旧图回归同机同网、固定样本，与当前包对比 P50／P95；若确认是客户端瓶颈，以 P95 下降至少 50% 为初步目标，按测量校准
签名轮换／参数顺序变化可信同对象同规格复用缓存；未知签名不被破坏；内容版本更新确实获取新图
快速滚动／切会话当前可见项优先，无消费者离屏任务及时取消，不错图、不阻塞新会话
容量与权限大量文件下清理不阻塞显示；缓存满、写失败、切号、退出、群历史清理及权限变化均回归
规格与动画列表、预览、原图独立正确；GIF、视频封面、横竖图、EXIF 与超大图片均正确

统计每组至少 50 个有效图片样本，跨多轮会话采样，分别报告 P50／P95 与成功率，不把缓存未命中、失败和超时从样本中静默删除。旧端、新端与参考软件的缓存状态必须标明；无参考账号和运行环境时，只报告我们自己的改善，不编造竞品 A/B 数字。

滚动帧时间、峰值内存、耗电与网络流量作为并列指标，不能仅以“看起来快”通过。保留一键诊断导出与功能回退，先小范围测试再扩展。
