# 易可聊双端原生重构方案

> 当前开发状态（0.3.0）：见 [功能与 UI 对齐记录](../原生功能与UI对齐-20261113/功能与UI对齐记录.md)。已补业务/媒体页面与安全登录恢复，按原版逐页核对；仍需真实账号与 Mac/iPhone 验收。


版本日期：2026-11-13（0.3.0 功能与 UI 对齐阶段）。用户已确定保留现有 uni-app UI，重构重点是性能、消息可靠性和 iOS 本地库同步。当前先完成本地开发与测试，没有独立测试服务；可借朋友的 Mac 验证，本机仍为 Windows。本方案区分目标架构、当前代码和仍需验证的内容。

## 1. 决策与开发方式

采用 Android Kotlin + Compose、iOS Swift + UIKit，两端直接接入固定版本的官方 OpenIM 原生 SDK，真实账号与现网兼容仍需互通验收。业务后端先沿用现有 Go 接口与账号体系，保留旧 uni-app 服务现有用户。原生页面逐页还原旧版本，复用布局、原图片、色值、文案和交互，不重做视觉设计。

在同一仓库的 `codex/native-bootstrap` 分支中增加 `IM-APP-android/`、`IM-APP-ios/`，保留 `IM-APP-fronend/`、`IM-APP-server/`。新目录承载独立平台工程，分支承载开发隔离；不是二选一。开发者同时维护旧版时可另建 worktree，避免来回切换影响未提交工作。当前改动尚未提交、合并或部署。

复用 UI 不等于复用 Vue 运行时：Compose / UIKit 重新实现原生列表、输入、媒体与生命周期。Vue 作为需求和视觉基准，核心聊天链路不套 WebView。协议等静态文字页可本地只读加载 HTML。

## 3. 目标架构

```text
原生 UI（复用现有 uni-app 外观）
    ↓ 状态快照 / 用户操作
会话与聊天业务层（分页、草稿、发送队列、消息归一化）
    ↓ 统一内部接口
OpenIM SDK adapter              现有业务 API adapter
    ↓                          ↓
SDK 管理的消息库与同步          现有 Go 服务 / 账号 / OSS
```

双端采用相同的业务契约和状态语义，共享 JSON fixture 与错误规范；不要求共享 UI 或把所有业务装进新的跨端框架。业务用户 ID 和 OpenIM 用户 ID 显式分开，不能将业务 ID 直接当 IM 账号。

OpenIM adapter 是替换与兼容边界。先核实旧 App、现网服务与自定义消息，再选择 SDK 版本，完成双端互通后固定依赖。竞品的定制包名和版本不是本项目可直接获取或兼容的证明。业务列表、媒体消息同时接受现有 camelCase / PascalCase 字段，由适配层归一化，不让命名差异散落到 UI。

## 4. iOS 本地库与同步治理

原生重构不能仅把登录和页面换掉就宣布解决同步。优先解决可重复的开库、同步中断和旧回调问题。

1. 将业务认证、SDK 登录、本地库可读、增量同步、实时连接分别建模；失败和超时不能伪装成同步完成。已有可读历史在同步重试时仍可浏览，并清楚显示连接状态。
2. 每次账号会话有 generation，每次同步有独立 attempt。退出、切号、重登和重试后，迟到的旧事件不得更新当前账号、列表或同步游标。
3. SDK 消息库只由 SDK 持有与迁移；业务层不并行写其私有表，不在失败后自动删库。自有业务缓存与 SDK 目录分开，目录按环境和账号隔离。
4. 在 iPhone 真机验证文件保护与锁屏可用性、后台切前台、进程重启、磁盘不足及数据库迁移。文件保护策略按内容敏感度与 SDK 支持能力选择，不能未经验证一律关闭保护。
5. Outbox 持久保存 client message ID、发送状态、重试依据和附件位置。发送结果不确定时先按 SDK / 服务能力对账，再决定重试，避免重复消息；不支持服务端幂等时必须显式处理限制。
6. 同步按会话分批更新 UI，限制事件合并窗口和并发，不在每条回调全量重排、全量读库或重建所有 cell。失败日志记录阶段、错误码、耗时和账号匿名标识，避免输出 token、密码和消息正文。

当前已将真实 SDK 初始化、登录、库可读查询、同步事件和前后台生命周期接入双端控制器。消息库由 SDK 独占；业务持久 Outbox 单独存储，先写盘再发送，重启时将未决发送恢复为“待核对”。服务已接受的消息须经 SDK 本地查询确认后才裁剪待发副本。找不到消息或本地 failed 不能证明服务未收到，因此不盲目重发。撤回 / 删除屏障用于阻止迟到历史恢复当前页面的原文。

iOS 账号目录使用首次解锁后可用的文件保护策略，自有 Outbox 通过 actor 串行持久化；旧会话 teardown 与新 SDK 会话串行隔离。以上是已实现的代码约束。当前没有 Mac，Swift / Objective-C 编译、锁屏开库和真实同步尚未运行，不证明 iOS 故障已彻底修复。旧版私有数据库迁移也没有完成。

## 5. UI 复用与性能工作

首轮按照旧 `sign-in.vue`、最终 `auth-modern.scss`、`ImTabBar`、`ConversationItem`、`ChatBubble`、`ImMessageComposer` 映射登录、导航、会话列表、文本聊天。底栏为“通讯录 / 聊天 / 我的”，发送按钮为“传送”。测试配置与样例入口移入 Logo 长按菜单，正常页面保留旧版结构。

本次已按用户授权连接现有后端，普通登录不需要进入调试菜单。默认 API 为 `https://www.xn--jprz53bj9s.com/api/v1`，对应现有 `www.易可聊.com`。登录调用 `POST /auth/login`，再用业务 accessToken 调用 `GET /me` 读取直接位于 `data` 的用户资料；成功后进入真实账号主页，“我的”显示真实昵称、账号与脱敏手机号。资料接口失败时仅回退本次登录响应的真实 `user` 并提示。若资料 ID 冲突，两端均不接收其他账号：Android 回退登录资料并提示，iOS 拒绝进入。

真实账号与离线样例严格分开。业务会话由 AndroidKeyStore / iOS Keychain 安全保存，不存密码，进程重启尝试恢复；过期或明确 401 最多刷新一次，先保存旋转凭据再继续业务。退出清除当前凭据并隔离旧请求结果，保留 SDK 消息库与待发记录。真实 IM 控制器按需调用一次 `POST /im/token`，Android 的 platformId 为 2、iOS 为 1，再使用返回的独立 IM userId 登录 SDK。断线、进入房间或资源未就绪错误不循环签发 Token，也不自动删库。

聊天页已补真实会话、历史、文字/图片/视频/语音/文件、名片/表情、引用/转发/收藏、搜索定位、群 @ 与置顶等；通讯录、好友/标签、群资料/权限/公告、个人资料、设置、二维码、群发及认证流程亦已接入现有接口。逐项实现与差异见双端 73 路由对照，不将代码存在等同运行通过。SDK 提交成功仅表示接受，不显示虚假“已送达 / 已读”。实时音视频、服务端离线推送、现网定制协议与覆盖迁移仍有独立门禁。

### 固定依赖与本轮协议范围

Android 固定 `io.openim:android-sdk:3.8.3.5` 与 `io.openim:core-sdk:3.8.3-patch10` 两个 AAR。发布 POM 不包含依赖，工程显式声明 Core；配对依据为官方 v3.8.3.5 tag 的构建文件。iOS 固定 `OpenIMSDK`、`OpenIMSDKCore` 的 `3.8.3-hotfix.15`，通过 CocoaPods 接入，并用薄 Objective-C bridge 明确真实 selector。精确来源与 SHA-256 在 `contracts/native-bootstrap/v1/sdk-dependencies.json`。竞品的 RepuSw fork 没有直接拿来作为本项目 SDK。

仓库部署声明的服务端为 `v3.8.3-patch.16`，这不是已读取线上容器版本的证明。两端当前读取单聊（1）和超级群（3），历史使用固定 wrapper 真正支持的 clientMsgID 游标、数量与 isEnd；返回的 lastMinSeq 没有对应请求参数，不能虚构传参。错误、空页或重复游标不能伪装“无更多历史”。

Token 响应的安全 HTTPS / WSS 地址直接保留。仅默认业务 origin 且精确命中已核实的旧 `8.154.44.197` 明文路径时，升级为现有域名的 `/openim-api` 和 `/openim-ws`；默认端口和一个尾斜杠可规范化，其他明文主机、非默认端口、userinfo / query / fragment 拒绝。不关闭 TLS 校验、不开放全局明文。

已接群保留 minVisibleSeq / revision、按成员清理边界与删除墓碑的单调持久过滤；撤回遵循业务 `/im/messages/recall` 和群权限，已读与自定义置顶按现有协议适配。这些仍需多角色真实账号与旧版互通验证。现有 `LoggingPushService` 仅记日志，登记 Token 不等于推送下发；不能宣称杀进程离线通知可用。

`rpx` 按窗口逻辑宽度 / 750 换算；旧固定 `px` 映射到 dp / point。原 Logo、底栏 SVG、头像和法律文档有可复核的资源 manifest，避免替换成近似图。详见 `docs/原生UI复用与验收-20261112.md` 与 `contracts/ui-parity/v1/`。

性能工作保留原视觉：消息列表分页、稳定 ID、增量刷新，按尺寸缓存图片与缩略图，后台解码和 I/O，进入聊天时先展示可读历史再补拉；键盘变化与历史加载保持滚动锚点。对文字、图片、长列表、群消息和媒体混合分别测量，不能用空列表或内存样例代替真实负载。

建议验收方法是同一设备、同一账号数据和网络脚本对比旧版与原生版，记录首屏、进入会话、历史分页耗时的 p50 / p95、滚动卡顿、峰值内存和崩溃。先量旧版基线再设门槛；目标应是更好的 p95 和更少长帧，具体数值由测试设备与业务规模确定，当前没有实测性能提升百分比。

## 6. 账号、本地记录与覆盖升级

复用原有账号与服务端不代表旧 App 本地库会自动迁移。需要分别清点服务器历史、仅本地历史、草稿、待发消息、附件和缓存；先在可回滚测试样本上验证，再开放迁移。

Android 正式覆盖升级必须使用现有 applicationId 和相同签名关系；iOS 使用原 Bundle ID、开发团队及应用记录，且需要验证 Keychain / App Group 等 entitlement。现在的独立 staging 包不会覆盖旧版，它用于保护本地测试，不是升级迁移验证包。

不要将不兼容的旧 OpenIM 数据库直接复制到新 SDK。优先使用 SDK 支持的迁移 / 导入机制；若只能重建可同步历史，必须先保全不能从服务端恢复的内容，并向用户说明真实范围。覆盖升级失败、迁移中断和回退版本对新库的兼容性都需要验证；卸载重装会影响沙盒数据，不能作为无损回滚步骤。

## 7. 后端兼容与部署顺序

当前没有修改 Go 后端、数据库结构、OpenIM 配置或线上部署。本轮 SDK 工作使用 481 份旧后端 / 前端源码和配置的 SHA-256 基线核对；结果见当前验收记录。上一轮登录修复另保留其 539 份基线记录，数量与范围不能混用。此前已有的并行修改保留，不归入本轮 SDK 修改。

后续确需后端改动时，优先新增接口或可选字段，保持旧请求、字段类型、错误语义和 ID 映射；新旧版本并行期间不删除旧列或旧路由。迁移采用先扩展、后回填、再切换，先测锁影响、耗时与数据恢复。新功能以默认关闭的开关或测试账号白名单逐步启用。

部署顺序为：独立测试环境与合成数据 → 旧客户端兼容回归 → 兼容后端 → 原生内测 → 小范围灰度 → 逐步放量。验证登录与互踢、消息、已读、媒体、推送、群规则及服务负载。异常先关新功能或停放量；不能只靠回滚二进制撤销数据库迁移。当前不能预先保证未来后端改动绝对零影响，但本轮没有上线任何变更。

## 8. Android 本地打包与分发步骤

原生工程不再通过 uni-app 云打包。Android 可以在当前 Windows 本地构建，也可以在配置好的 CI 上构建。

1. 使用 D 盘 JDK 与 Android SDK；本地已复用 `D:/JDK17`、`D:/Android/SDK`。Gradle、临时目录及模拟器数据放 `.native-cache/`，不把依赖下载到 C 盘。
2. 在仓库根目录运行已有构建脚本。离线模式要求已有缓存，新机器首次解析依赖时去掉 `-Offline`。

```powershell
& ./IM-APP-android/build.ps1 -Tasks @(':app:testDebugUnitTest', ':app:assembleDebug', ':app:lintDebug', ':app:assembleDebugAndroidTest') -Offline
```

3. 取得 `IM-APP-android/app/build/outputs/apk/debug/app-debug.apk`，安装独立 staging 包。新版 `0.3.0-parity` / code `4` 可覆盖之前的原生测试包，无需卸载，不覆盖正式 uni-app。安装后直接使用现有账号密码、选择区号、勾选协议登录；默认连接上述现有 HTTPS 后端。Logo 长按仍可覆盖 HTTPS 地址或进入不联网的样例。正常业务登录后按需申请 IM Token 并启动真实 SDK。首次登录建议使用受控账号；同平台旧客户端是否互踢取决于现有服务策略，本轮没有修改该策略。
4. 正式签名前核对现网 applicationId、签名指纹、versionCode、自定义消息、推送与旧库迁移。签名 keystore 和密码通过本地受控配置 / CI secret 注入，不提交仓库。
5. 另行接入经过评审的 Release 配置和签名流程，届时用 `assembleRelease` 生成签名 APK，或 `bundleRelease` 生成 AAB；检查 APK / AAB 签名、安装升级和实际渠道的目标 API、原生库 ABI / 页大小要求。当前所有 Release 构建显式阻止，不应删除检查后直接发包。
6. APK 走授权下载渠道，AAB 走商店后台，先内测轨道再灰度。客户端发布与后端部署是两个流水线；只更新客户端不要求重新部署整套服务。

## 9. iOS 打包、TestFlight 与上线步骤

iOS 编译、签名和 Archive 需要 macOS + Xcode，可使用团队 Mac 或经过配置的云端 macOS CI。Windows / HBuilderX 云打包不能直接代替本原生工程的 Xcode 流程。本机没有 Mac，提供 `IM-iOS-0.3.0-mac-check.zip`，可直接在朋友 Mac 上验证；当前未生成可安装 IPA。详细步骤见 [Mac 与 iPhone 验证](../iOS-Mac验证步骤.md)。

1. 在朋友 Mac 解压本次源码交接包（本次改动尚未提交，单独拉远端旧分支可能缺失），执行 `bash IM-APP-ios/scripts/verify_on_mac.sh`，或按以下手动步骤。安装符合项目和当期 Apple 提交要求的 Xcode、Ruby / Bundler，并按工程 Gemfile 安装 CocoaPods 1.16.2。进入 `IM-APP-ios` 目录执行 `bundle config set --local path vendor/bundle`、`bundle install`、`bundle exec pod install --repo-update`。必须打开生成的 `IMNative.xcworkspace`，使用共享 `IMNative` Scheme；不能仅打开 xcodeproj 绕过 SDK 依赖。不将 Pods、生成 workspace、DerivedData 或签名文件提交 Git；第一次在 Mac 解析后审查并提交 Podfile.lock。
2. 先运行无签名本地检查与模拟器构建；Package 的 XCTest 需显式执行 `swift test`，不能把空的 Xcode TestAction 当成已跑测试。

```bash
swift test --package-path IM-APP-ios/Packages/IMCore
xcodebuild -workspace IM-APP-ios/IMNative.xcworkspace -scheme IMNative \
  -sdk iphonesimulator -configuration Debug \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath .native-cache/DerivedData CODE_SIGNING_ALLOWED=NO build
```

3. 开发者账号准备好后，为独立内测身份配置 Team、开发签名和授权的测试 iPhone，验证真机库、锁屏、键盘、后台、推送和网络切换。模拟器 Debug 不能安装到 iPhone。
4. 正式升级使用现有 App Store Connect 应用和 Bundle ID，核对证书、Provisioning Profile、版本 / Build、推送 entitlement、隐私清单、必要权限及 SDK 合规材料。证书与 App Store Connect API key 放受控配置，不进 Git。
5. 迁移和互通门禁通过后，专门修改当前 Release / Archive 阻断，接入正式签名。Xcode 选择通用 iOS 设备 → Product / Archive → Organizer / Validate App → Distribute App / App Store Connect。需要 CI 时采用同等 `xcodebuild archive` 和 `-exportArchive`，并以团队实际 profile 生成 ExportOptions，不能填占位签名配置直接运行。
6. App Store Connect 等待处理后分发 TestFlight，完成内外部测试与审核，再提交 App Review，选择手动或分阶段发布。企业 / Ad Hoc 分发仅在具有对应资质和设备授权时另配，不是默认部署方式。

原生功能变更通过新的 APK / AAB / IPA 发布；原来的 WGT 热更新不能用于更新 Swift / Kotlin 原生代码。服务端配置与兼容接口可独立发布，但不能借配置绕过原生应用的版本与审核流程。

## 10. 本地验证、CI 与开发顺序

```powershell
python -X utf8 scripts/native/verify_contracts.py
python -X utf8 scripts/native/verify_ui_parity.py
python -X utf8 IM-APP-ios/scripts/verify_project.py
```

现有 GitHub Actions 包含契约校验、Android 测试 / Debug 构建 / Lint、Mac XCTest / 模拟器构建；本轮增加 UI 素材来源校验。当前未推送或触发远程运行，也没有生产发布 job。

| 阶段 | 工作 | 放行依据 |
| --- | --- | --- |
| 当前 0.3.0 开发 | 固定 SDK、安全登录恢复、媒体与业务流程、持久 Outbox、73 路由逐页对齐 | Android 构建/单测/Lint、设备媒体与合成页面检查；iOS 静态检查，真实账号和 Mac 待验 |
| 真实互通验收 | 受控账号双端互发、旧版共存、弱网、超时、重启与锁屏、群规则 | 双端真机与失败恢复记录 |
| 业务与旧 UI | 以 73 条旧路由清单逐页还原，完成媒体、群、好友、收藏、设置、推送 | 逐页状态 / 截图验收和真实业务回归 |
| 迁移与性能 | 旧签名覆盖升级、仅本地数据保全、iPhone 专项、同负载性能对比 | 真机迁移和性能门槛 |
| 发布 | 内测、TestFlight / 商店测试轨道、兼容后端、灰度 | 旧版兼容、可观测指标和回退演练 |

当前包的测试数量、SHA-256、逐页差异及截图证据以 [本次对齐记录](../原生功能与UI对齐-20261113/功能与UI对齐记录.md) 为准。Android 在断网模拟器实际执行原生 Core smoke、AndroidKeyStore 验证、图片解码与 GIF 帧推进/离页停播，并渲染实际业务页面的合成资料；不包含真实账号登录、WebSocket 认证或消息互通。iOS 静态与语法检查不能代替 Mac 编译和 iPhone 运行。

真实服务只读 HTTP 探测中，`GET /openim-api/` 返回 404 JSON、`GET /openim-ws` 返回 200 JSON，采用默认 TLS 校验；未带凭据、未做认证 WebSocket 握手。HTTP 可达不能证明真实 IM 互通。没有使用合成账号向生产提交登录或短信请求。

当前 Android 测试包为 `0.3.0-parity` / code `4`，仍为独立 staging 身份；iOS 为 `0.3.0` / build `4`，未生成 IPA。Android 最终哈希、大小及检查记录以本次对齐记录和 verification.json 为准。本轮没有上线后端或发布客户端，旧版继续运行；实际测试时同账号同平台可能触发现有互踢策略。
