# IM 运维平台 — 团队共享部署与安全说明

本文说明：为什么要共享部署、怎么部署、账号从哪来、开放成线上地址有哪些风险、以及怎么降低风险。

配套本地开发说明见 [USAGE.md](./USAGE.md)；上游完整手册见 [docs/USER-GUIDE.md](./docs/USER-GUIDE.md)。

---

## 1. 为什么要部署一份共享实例

每人在自己电脑 `npm run dev` 时，知识库、Redis/数据库连接等存在本机 `DATA_DIR`（默认 `./data`）里，**不会随 Git 同步**，队友默认看不到。

要「配一次、大家共用」，需要：

1. 在一台大家都能访问的机器上跑 **一份** Viron Full 服务；
2. 用 **组织工作空间**（不要只在个人空间）放知识库和连接；
3. 给成员发账号并做资源授权。

---

## 2. 部署步骤（Docker Compose Full）

### 2.1 环境要求

- Docker 24+、Docker Compose v2
- 服务器可被队友网络访问（内网 IP / 公网 IP / 域名）
- 建议开放端口：`8080`（或经 Nginx/Caddy 反代到 443）

### 2.2 配置 `.env`

在服务器进入本目录：

```bash
cd /path/to/IM-ops/viron
cp .env.example .env
```

至少修改：

```dotenv
HOST=0.0.0.0
PORT=8080
DATA_DIR=./data
DATABASE_DRIVER=sqlite
ADMIN_USERNAME=admin
ADMIN_PASSWORD=换成足够强的密码
ALLOW_WEAK_PASSWORDS=false
COOKIE_SECURE=false
```

| 变量 | 说明 |
|------|------|
| `HOST` | `127.0.0.1` 仅本机；对外访问必须 `0.0.0.0` |
| `ADMIN_*` | **仅首次初始化**时创建平台管理员（见第 3 节） |
| `COOKIE_SECURE` | 纯 HTTP 用 `false`；前面有 HTTPS 反代时改为 `true` |
| `DATABASE_DRIVER` | 小团队可用 `sqlite`；人多再迁 MySQL（见手册 18.2） |

**不要**把 `.env`、`data/`、`master-key` 提交到 Git。

### 2.3 启动与检查

```bash
docker compose -f docker-compose.full.yml up -d --build
curl http://127.0.0.1:8080/healthz
```

健康检查应返回 `status: "ok"`、`product: "viron"`。

队友浏览器访问：`http://服务器IP:8080`（有域名则用域名）。

### 2.4 建组织并共享资源

1. 用管理员登录 → **组织与用户** → **创建组织**（如「IM 运维组」）
2. **邀请**页生成邀请链接发给队友（加入组织前，对方需已有可登录账号，见第 3 节）
3. 左上角切换到 **组织工作空间**（不要停在「个人空间」）
4. 在组织空间中：建环境 → 建/复制 SSH、数据库、Redis 连接 → 关联环境 → 上传知识库
5. 对成员或项目组做 **资源授权**（环境 / SSH / 数据库 / Redis）

个人空间里已有内容**不会自动出现**在组织空间；需在组织空间重建，或使用「个人资源复制进组织」。

### 2.5 备份（必做）

持久化在 `DATA_DIR`，至少包含：

- `envman.db`（或外部 MySQL 元库）
- `master-key`（加密凭据的主密钥，丢了等于连接密码无法解密）
- `recordings/`、`backups/` 等按需

备份必须同时包含数据库与 `master-key`；不要在线零散拷贝正在写入的 SQLite。

## 3. 账号密码是不是固定的？

**不是长期写死的一组账号，但首次有默认引导值。**

### 3.1 本仓库（IM 运维改造版）的实际行为

| 能力 | 现状 |
|------|------|
| 自主注册 | **已关闭**。接口直接返回「自主注册已关闭，请联系管理员」 |
| 首次管理员 | 库里还没有任何平台管理员时，用 `.env` 的 `ADMIN_USERNAME` / `ADMIN_PASSWORD` **创建一次** |
| 之后改 `.env` 密码 | **不会**自动改已有账号密码；要在平台里改密，或由管理员重置 |
| 谁能登录 | 当前登录逻辑要求账号为 **平台管理员**（`is_platform_admin`）且状态为 active |
| 队友账号 | 由已登录的平台管理员在 **组织与用户 → 平台账号** 中创建；创建时勾选「平台管理员」，否则无法登录 |

开发文档里常见的默认值（仅作首次本地参考，上线务必改掉）：

| 字段 | 示例默认值 |
|------|------------|
| 用户名 | `admin` |
| 密码 | `Change-me-before-start-1` |

密码策略（`ALLOW_WEAK_PASSWORDS=false` 时）：至少 10 位，且在大小写字母、数字、特殊字符中至少满足 3 类。

### 3.2 推荐发号方式（团队）

1. 管理员用强密码登录共享实例  
2. **平台账号** 为每位同事创建独立用户名 + 初始强密码，并设为平台管理员  
3. 同事登录后立刻改自己的密码  
4. 再加入同一组织，切到组织工作空间使用共享资源  

不要全员共用同一个 `admin` 密码；出问题无法审计到人，泄露后也无法单独吊销。

## 4. 开放成线上地址，会不会有安全风险？

**会。而且风险比普通业务后台更高。**

本平台登录后可操作 SSH、数据库、Redis、日志、知识库里的部署说明等。一旦被未授权访问，等同于拿到运维入口。

### 4.1 主要风险

| 风险 | 说明 |
|------|------|
| 弱口令 / 默认密码被扫 | 公网暴露后，默认 `admin` + 弱密码会被自动化爆破 |
| 运维能力被滥用 | 登录成功即可连生产库、Redis、SSH（取决于你配了什么） |
| 凭据落库被拖 | `DATA_DIR` 含加密连接密码；若服务器被入侵且 `master-key` 一并失窃，可解密 |
| 中间人窃听 | 纯 HTTP 时 Cookie/密码可能被嗅探（尤其公共 Wi‑Fi） |
| 误暴露审计与知识库 | 部署文档、内网地址、账号说明若写在知识库，等同二次泄密 |

### 4.2 上线前最低安全要求（建议全部做到）

1. **改掉首次管理员密码**，禁用弱密码（`ALLOW_WEAK_PASSWORDS=false`）  
2. **一人一账号**，不用共享 `admin`；离职即停用账号  
3. **优先内网或 VPN**，不要无防护地裸奔公网；必须公网时加 IP 白名单 / 零信任 / 反代鉴权  
4. **HTTPS**：Nginx/Caddy 终止 TLS，并设 `COOKIE_SECURE=true`  
5. **防火墙只开必要端口**；数据库、Redis、SSH 不要因 Viron 而额外对公网放开  
6. 连接池里的业务账号尽量用**最小权限**（只读账号做排查，写账号严控）  
7. 定期备份 `DATA_DIR`（含 `master-key`），并限制服务器 SSH 登录范围  
8. 关注 **操作审计**；异常登录及时改密并停用账号  

### 4.3 推荐部署形态（从安全到便利）

| 形态 | 适用 | 说明 |
|------|------|------|
| 仅内网 / VPN | **最推荐** | 队友连公司 VPN 后访问 `http(s)://内网IP:8080` |
| 公网 + HTTPS + IP 白名单 | 小团队分散办公 | 只允许办公室/家庭出口 IP |
| 公网裸 HTTP + 默认密码 | **禁止** | 极高风险 |

## 5. 最短检查清单

部署：

- [ ] 服务器 Docker 已就绪，`.env` 中 `HOST=0.0.0.0`，管理员强密码已改  
- [ ] `docker compose -f docker-compose.full.yml up -d --build` 成功，`/healthz` 正常  
- [ ] 已创建组织，共享资源建在**组织工作空间**  
- [ ] 已为队友创建平台管理员账号并授权资源  

安全：

- [ ] 未使用文档默认密码上线  
- [ ] 自主注册保持关闭（本仓库已关闭）  
- [ ] 访问路径为内网/VPN，或公网 HTTPS + 访问限制  
- [ ] `DATA_DIR`（含 `master-key`）有备份且权限收紧  
- [ ] 未将 `.env` / `data/` 提交仓库
