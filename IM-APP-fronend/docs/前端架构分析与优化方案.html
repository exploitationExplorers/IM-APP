IM 前端（IM-APP-fronend）架构分析与优化方案

分析日期：2026-10-16 ｜ 基线：7cf95f7（wgt 1.0.114 / 214）｜ 本文只做分析，不改代码

范围：整体代码与流程梳理、App 端图片/视频加载慢的根因、"像微信一样本地缓存"的可行方案、昨天（10-15）缓存尝试导致 iOS 闪退的复盘、代码规范检测结果与整改路线。

0. 结论速览

  1. 图片/视频慢，主因不是"没有本地缓存"，而是下面四件事叠在一起：
    • 图片消息没有真正的缩略图：发送时把同一张原图同时写进原图、大图、缩略图三个字段，列表里每个气泡加载的都是原图；
    • App 端每张图会被下载两次：<image> 下一次，uni.getImageInfo 为了算气泡宽高又下一次，而宽高其实消息里本来就有；
    • 图片地址 /object/... 每次都要先经过 OpenIM API 中转，nginx 上也没配缓存头，WebView 很难命中缓存；
    • 发图时同一张图压缩了两次，多张图串行发送，而且要等压缩完才出现占位气泡。
  2. 聊天记录在 App 端其实已经存在本地：原生 OpenIM SDK 初始化时传了 dataDir，消息存在手机本地的 SQLite 库里。问题出在服务器或网络断开时，ensureIMLogin 会先请求业务后端换 IM token，请求失败后 SDK 根本没有初始化，本地库也就读不到。H5 端则没有可靠的本地库。
  3. 昨天 1.0.111 的 iOS 闪退：真正发给客户的只有"消息本地缓存"（用 uni.storage 再存一份消息），图片缓存还没发布就回滚了。闪退的直接原因因为没有崩溃日志，目前无法 100% 确定；可疑点是同步存储写入过于频繁、登录前就用缓存渲染这两条路径（详见第 4 节）。更根本的问题是：
    • 方案方向有误：App 端已经有原生 SQLite，又在 uni.storage 里复制了一份；
    • 没有功能开关，没有灰度，一发布就推给了全部客户。
  4. 代码规范：4 个超大文件（openim.ts 3443 行、room.vue 3075 行、chat.ts 1752 行、ChatBubble.vue 1478 行）占全部代码的 22%。ESLint 检出 251 个问题，vue-tsc 类型检查当前不通过（3 个错误），重复代码占 3.9%，有 281 处静默吞掉的异常，isAppPlatform 被重复实现了 8 份。项目没有 ESLint / Prettier / 提交门禁 / CI。
  5. 建议顺序：先改发布流程止血（灰度 + 崩溃日志）→ 服务端零风险提速（缩略图 + 缓存头）→ 客户端低风险提速（直接用消息自带宽高、去掉二次压缩、占位气泡提前）→ 带开关的媒体缓存 → 引入规范工具链、拆分大文件。

2. 核心流程梳理

2.1 启动与登录

main.ts  installH5MediaProxy()（H5 改写 http 媒体地址为同源）
   │
App.vue onLaunch
   ├─ setAuthExpiredHandler → 401 统一失效
   ├─ userStore.bootstrap()  读 im_token，拉 /me
   ├─ checkAndPromptAppUpdate()  wgt 热更新检查
   └─ H5: visibilitychange → chatStore.resyncAfterResume()
App.vue onShow
   └─ setupAppAuthGuard / 拉好友申请 / resyncAfterResume（3 秒节流）

2.2 IM 登录（ensureIMLogin，openim.ts）

ensureIMLogin()
  ├─ 缓存有效（imUserId + token 未过期 + connected + 业务 token 未变）→ 直接返回
  └─ doLogin()
       ├─ fetchIMToken()  ← 每次都请求业务后端 /im/token（断网/后端挂 → 这里就失败）
       ├─ App: InitSDK({ dataDir: 按用户隔离的本地目录, apiAddr, wsAddr })
       ├─ GetLoginStatus 已登录同一用户 → waitForSync(15s)
       └─ loginSdk() → Login → waitForSync()

关键点：App 原生 SDK 有本地 SQLite（dataDir），但只要 fetchIMToken 失败，后面的 InitSDK 根本不会执行，所以"断网看不到历史"并不是缺本地库，而是登录链路强依赖在线。

2.3 会话列表与实时消息

chat/index.vue → chatStore.loadConversations()
  ├─ ensureIMLogin → 并行 getConversationList + 同步黑名单
  ├─ reconcileExitedGroups → decorate → 排序
  └─ subscribeRealtime()：OnRecvNewMessage(s) / OnConversationChanged / 撤回 / 已读回执 ...
        └─ ingestIncoming → appendMessage → patchConversation（预览、未读）

2.4 进入聊天室（room.vue onLoad）

ensureIMLogin
  ├─ enterTask: chatStore.enterConversation()（业务 ID → OpenIM ID、权限预检）
  └─ loadTask : chatStore.loadMessages()  ← 与 enterTask 并行
        └─ getHistoryMessages(PAGE_SIZE=20, ViewType.History) → toChatMessage → messagesMap
渲染：倒置 scroll-view（scaleY(-1)），只挂载尾部 48 条（RENDER_TAIL），上翻每批扩 40 条
内存：单会话 200 条（在房翻历史最多 400 条），rawMessages 300 条

2.5 发送图片（App）

pickLocalImages()
  ├─ 华为/鸿蒙: plus.gallery.pick → _doc/gallery/
  ├─ 其他: uni.chooseImage(sizeType: ['original','compressed'])
  └─ materializePickedPaths(): 逐张串行 materializeAppLocalImage()  ← 第 1 次 compressImage
room.vue sendPickedImagePaths(): for...await 串行，每张：
  chatStore.sendImage()
    └─ openim.sendImageMessage()

         ├─ CreateImageMessageFromFullPath → SDK 上传 → 发送

                     （source/big/snapshot 三个字段填同一个 URL）

2.6 图片展示（ChatBubble.vue）

toChatMessage: pictureCandidateList() 优先 snapshot → source → big …（但三者通常是同一原图）
ChatBubble:
  imageSrcCandidates → imageDisplaySrc → <image :src>      ← 下载 1 次（WebView）
  watch(mediaSrc) → measureMediaSize() → uni.getImageInfo  ← App 端再下载 1 次（并发 3）
  量到尺寸前用 280×210 占位，量到后改尺寸 → 气泡高度跳变

2.7 视频

  • 气泡：只显示 snapshotUrl 封面；封面失败时不在列表里截帧（这是对的）。
  • 播放：video-viewer.vue 用远程 URL 流式播放，没有本地缓存；iOS 的 AVPlayer 对 MinIO / OpenIM 对象地址的 Range 支持不稳定（语音那边已经因为这个改成"先下载再播"）。

pack-wgt.cjs --publish 默认发到 channel=test，而客户手里装的就是 test 壳，相当于没有灰度。docs/测试环境与发布门禁.md 已经给出 canary 渠道方案，但还没落地。

3. App 端图片/视频慢：根因分析

# 根因 证据 影响 端
R1 没有真缩略图，列表加载的是原图 openim.ts 中 sendImageMessage / sendImageMessageViaUpload / ensurePictureSourceUrl 都把 sourcePicture / bigPicture / snapshotPicture 填成同一个 picture 一张 3~5MB 的手机照片在列表里按原图下载、解码，群里图一多就排队 全端
R2 每张图下载两次 ChatBubble.vue 的 measureMediaSize 对每个图片/视频封面调用 uni.getImageInfo；App 端遇到网络图片会先下载到临时目录 流量和耗时翻倍，而且 3 路并发的测量队列会拖住首屏尺寸，气泡高度还会跳 App
R3 宽高信息没用上 PictureBaseInfo 里本来就有 width/height（发送时 imageSizeOf 已经写入），但 ChatMessage 类型里没有宽高字段，映射时丢掉了 只能靠 R2 去测量 全端
R4 对象地址无法被缓存 nginx location ^~ /object/ 直接代理到 OpenIM API(10002)，没有 expires / Cache-Control；OpenIM 的对象接口通常是 302 跳转到带签名、会过期的 MinIO 地址（需在服务器上用 curl -I 验证） WebView 缓存命中率低；每张图都要多走一次 API 往返 全端
R5 发图双重压缩 + 串行 pickLocalImages → materializePickedPaths 压一次，sendImageMessage → prepareAppChatImagePath 再压一次；sendPickedImagePaths 用 for…await 逐张发 选完图要等很久才出现气泡，多图更明显；这是为修鸿蒙 4 content:// 加的通用路径，所以 iOS 也受影响 App
R6 占位气泡出现得晚 物化/压缩全部完成后才进 chatStore.sendImage 创建占位 体感上"点了没反应" App
R7 视频没有缓存，iOS 流式播放不稳 video-viewer.vue 直接给远程 URL 每次打开都重新缓冲 App

3.1 为什么 R1~R4 比"本地缓存"更值得先做

  • 微信的"快"首先来自列表只加载缩略图（几十 KB），点开才加载大图；本地缓存解决的是"第二次打开快"。
  • 我们现在列表加载的是原图，并且下载了两次。就算做了本地缓存，第一次打开依然慢，缓存目录也会被原图迅速撑大。
  • R1~R4 的改动基本在服务端配置和数据映射层，不涉及文件 IO，闪退风险接近于零。

4.2 消息缓存（已上线）可疑点

没有拿到 iOS 崩溃日志，以下按可能性排序，需要日志确认。

可疑点 说明 可能性
同步存储写入风暴 每条新消息（任何会话）都会触发 persistConversationMessages（每个会话一个 400ms 防抖）和 schedulePersistConversations（500ms）。每次写消息会执行 JSON.stringify(120 条) + setStorageSync，再加上 touchMsgIndex 的一读一写，也就是 3 次同步桥接调用。登录后 OpenIM 会批量推送离线消息，几十个群同时触发写入，JS 线程被同步 IO 堵死 → 界面卡死 → iOS 看门狗（0x8badf00d）杀进程 高
登录前就用缓存渲染、流程变化 loadConversations 在 ensureIMLogin 之前先把缓存会话塞进列表；room.vue 在登录前先灌入缓存消息；enterConversation 新增了离线分支和占位会话。缓存数据和 SDK 状态不一致时，后续逻辑可能进入未覆盖的分支（白屏/"打不开"） 中
缓存数据失效 缓存里会存下 App 发送时的本地临时路径（_doc/uniapp_temp_xxx），冷启动后这些文件已不存在；还有已撤回/已删除的消息 低（不会闪退，但会显示异常）

4.3 图片缓存（未上线）的设计风险——下次必须避开

风险 代码表现 后果
无并发上限的批量下载 loadMessages 后遍历全部消息，对每张图调用 ensureChatImageCached；每个气泡的 watch(immediate) 也会触发；收到图片消息还会触发 进一个图多的群会瞬间发起上百个 uni.downloadFile + plus.io 拷贝，iOS 内存超限（JetsamEvent）被杀
预取整页历史 不是"看到才下载"，而是"加载到就下载" 流量浪费 + 加剧上一条
渲染路径上同步读大 JSON peekChatImageCache 每次都 readIndex() 解析整张索引（最多 300 条），而每个气泡的计算属性都会调用它；touchIndex 每张图都要读 → 排序 → 整表写回 滚动卡顿，和存储写入风暴叠加
下载的是原图 因为 R1，缓存进去的全是原图 300 张原图可能占 1GB+，索引淘汰时又有大量删除 IO
失败也返回"成功路径" copyTo 失败时直接 resolve('_doc/chat_img/xxx')，并不确认文件是否存在 会显示坏图，进而触发 onImageError 回退
H5 blob URL 永不释放 URL.createObjectURL 生成后只在清缓存时 revoke H5 长时间使用内存泄漏

4.4 方向性问题

  1. 重复造轮子：App 端原生 OpenIM SDK 已经把消息存进 SQLite，再拿 uni.storage（定位是 KV 小数据）存一份是错误的存储选型；正确做法是让原生本地库在离线时也能被读到（见 5.1）。
  2. 没有开关、没有灰度、没有崩溃监控：出问题只能整包回滚，而且要靠用户投诉才发现。
  3. H5 和 App 走同一套逻辑：违反了项目自己的跨端准则（AGENTS.md：跨端能力必须分平台分支）。

4.5 需要补的证据（建议尽快拿到）

  • iPhone：设置 → 隐私与安全性 → 分析与改进 → 分析数据，找 JetsamEvent-*（内存超限）或带 App 名的 .ips（看 0x8badf00d 看门狗 / EXC_BAD_ACCESS）。
  • 或者把手机连到 Mac，Xcode → Window → Devices and Simulators → View Device Logs。
  • 拿到日志后再决定缓存方案的细节；没有日志之前不要再上类似改动。

5. "像微信一样"本地缓存：推荐方案

5.1 聊天记录（文字等）

端 方案 风险
App 不再自建消息缓存。改造 doLogin：成功登录后把 { userId, imToken, apiAddr, wsAddr, platform, expireAt } 安全地保存在本地；下次启动如果 fetchIMToken 因网络失败，就用保存的参数先 InitSDK + Login，原生 SDK 会初始化本地库，GetAdvancedHistoryMessageList 直接读 SQLite；联网后 SDK 自动重连并补齐数据。UI 层把"离线"做成顶部提示条，而不是 toast 报错清空页面 低（需先验证：原生 SDK 在 WS 连不上时 Login 能否返回、本地查询能否正常）
H5 WASM SDK 本身也用 IndexedDB（取决于 SDK 版本），断线时 SDK 直接返回 10000。H5 是辅助端，建议只做"不清空已加载内容 + 断线提示"，不做持久化离线历史 低

5.2 图片/视频（媒体缓存）

前置条件：先完成第 3 节的 R1~R4。没有缩略图就做缓存，等于把原图塞满手机。

设计要点（App 专用，H5 继续依赖浏览器 HTTP 缓存 + 正确的缓存头）：

MediaCacheService（独立模块，可远程开关）
├─ 只对"进入可视区域"的气泡发起下载（IntersectionObserver / 渲染窗口内）
├─ 全局下载队列：并发 ≤ 2（iOS）/ 3（Android），进房时清空旧会话队列
├─ 列表只缓存缩略图；大图在预览时才下载，并单独设上限
├─ 索引：plus.sqlite（或单个 JSON 文件 + 内存 Map + 批量异步写），渲染路径只查内存
├─ LRU 按总字节淘汰（例如缩略图 200MB、大图 500MB），淘汰在空闲时分批执行
├─ 落盘以"下载成功 + 文件真实存在"为准，失败不写索引
├─ 路径：统一 plus.io.convertLocalFileSystemURL 转绝对路径再交给 <image>
├─ 开关：远程配置 media_cache_enabled（默认关），按渠道/用户比例放量
└─ 观测：命中率、下载失败率、缓存目录大小，打点上报

可选的更彻底方案：用原生图片缓存插件（如基于 SDWebImage / Glide 的 uni 原生插件），或把聊天列表改成 nvue 页面使用原生 <image> 的磁盘缓存。这样效果最好，但需要重新打原生基座，工作量也最大。

5.3 视频

  • 列表只显示封面（已经是这样）；
  • 播放前先下载到 _doc/video_cache/ 再用 file:// 播放（与语音同一套思路），并设总量上限；
  • 大视频：先流式播放，同时后台下载，下次直接读本地。
