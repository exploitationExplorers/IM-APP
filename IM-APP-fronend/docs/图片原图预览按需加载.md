# 图片原图预览按需加载

## 只读调试结论（2026-10-18）

用户现象：Android、iOS 首次点开大图约 5 秒，第二次快；退出重进聊天后再次加载。H5 也能复现首次慢。

在用户指定的正式群只读查看，未发送消息或修改群设置；未拦截请求、未禁用 HTTP 缓存。实际观察：

| 项目 | 本次结果 |
| --- | --- |
| 首次点开一张图片 | 16 次原图 resolver 302，随后 16 次 OSS 200 |
| 原图传输合计 | 10,056,623 bytes，约 9.6 MiB |
| 最慢原图请求 | 9,815.88 ms，包含排队时间 |
| 重复内容 | 同一对象出现 7 次传输，对应不同 resolver / 签名地址 |
| 第二次预览、退出重进 H5 | 本次未观察到重新传输 OSS 图片 |

这些是本次网络条件下的观测，不是所有设备的固定耗时。PC 线上检查使用了暖缓存，不能当作冷启动性能数据。历史失败图片不在本次范围。

**已确认根因**：当前固定版本的 uni H5 `ImagePreview` 一次挂载整个 `urls` 列表的 `ImageView`，每个组件立即创建原图 `img`。点开一张图会抢下其他原图，并因不同签名地址产生重复下载、争抢连接和带宽。

**尚未确认**：App 退出重进时重新下载的原因。H5 本次未复现，不能直接用本结论解释原生 App；也不据此修改 OSS 权限、缓存响应头或开启全局媒体缓存。

## 修复范围与跨端边界

- `scripts/fix-uni-h5-preview.cjs` 对 `@dcloudio/uni-h5@3.0.0-5020320260806002` 的 ES 实现施加幂等补丁。
- 保留完整 Swiper 列表，仅为当前及本次预览中访问过的页面创建 `ImageView`，回滑保留已挂载的图片。
- 不改 uni 的 Swiper、缩放、关闭实现，不取消左右切换功能。不新增图片预下载，不重写 OSS URL 或签名参数。
- 在 `postinstall` 及 H5 Vite 启动/构建时应用；依赖版本或上游代码形状变化时明确报错，要求重新审查，不能静默跳过。
- `previewImagesWithSave` 的运行逻辑、原生 `uni.previewImage`、长按保存接口不变；未修改消息字段解析，保留已有 camelCase / PascalCase 兼容。
- 这是 **H5 的已确认问题修复**，不声称已解决 Android/iOS 原生预览或跨会话磁盘缓存问题。



## 后续原生端定位
