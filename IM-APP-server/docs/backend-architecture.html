业务后端不是聊天引擎

IM-APP-server 管账号、关系、权限、文件元数据和 OpenIM 桥接。 真正的消息收发、历史、会话、已读、离线走 OpenIM WebSocket + MongoDB。 Go 进程里同时跑 HTTP API、IM 同步 Worker、Kafka Outbox 发布器和万人转发 Worker。

Go 1.25 + Gin 1.10 PostgreSQL / pgx 连接池 Redis 限流 + Token 缓存 MinIO 预签名直传 OpenIM REST 桥 + Webhook Kafka 异步转发 推送仍是日志桩 旧 /ws 默认关闭

Go 管什么

多国手机号注册、JWT、资料、公开 ID、二维码、好友申请、拉黑、群设置、禁加好友、文件元数据、OpenIM Token、对象解析、Outbox 同步、发送前权限 Webhook、万人转发任务。

OpenIM 管什么

单聊/群聊消息、历史、会话列表、已读、离线补偿、在线状态、@ 提醒。消息正文不进 PostgreSQL，Go 也不直连 OpenIM 的 MongoDB。

明确不做

转账钱包、红包、朋友圈、音视频通话、PC/H5 正式版。旧 Go /ws 与 PostgreSQL 消息 REST 仅 LEGACY_CHAT_ENABLED=true 才注册。

分层硬约束

handler 只绑定入参、调 service、把 sentinel error 映射成中文 HTTP。service 不碰 *gin.Context。repository 只写 SQL，不做权限语义。跨层不得跳级。

// cmd/server/main.go 装配示例
userRepo := &repository.UserRepo{DB: pool}
userSvc  := &service.UserService{Users: userRepo, ...}
userH    := &handler.UserHandler{Svc: userSvc}

统一响应

一律 {code, message, data}。code 只有 0/1，语义由 HTTP 状态码承担。禁止 handler 裸 c.JSON（Webhook 是例外：OpenIM 要求它自己的 envelope）。

func OK(c *gin.Context, data interface{}) {
  c.JSON(200, Body{Code: 0, Message: "ok", Data: data})
}
身份映射：业务用户 UUID a1b2-...-c9 → OpenIM userID 去掉连字符 a1b2...c9。反向也必须能还原成合法 UUID，否则 Webhook 直接拒绝——防止非本 App 账号混入。

func AuthRequired(secret string) gin.HandlerFunc {
  return func(c *gin.Context) {
    raw := strings.TrimPrefix(c.GetHeader("Authorization"), "Bearer ")
    claims, err := ParseToken(secret, raw) // HS256, uid in claims
    if err != nil { response.Unauthorized(c, "登录已过期"); c.Abort(); return }
    c.Set(ContextUserID, claims.UserID)
    c.Next()
  }
}

Access Token TTL = 2 小时；Refresh Token 随机 32 字节，哈希入库，30 天。刷新时旧 refresh 立即失效。

账号唯一键是 countryCode + 本地号，入库标准化为 E.164。接口返回只有脱敏号 phoneMasked，不能按手机号搜索。

代码要点

  • 验证码存 SHA-256，明文只在开发环境回传 devCode。
  • 密码 bcrypt；不传密码则 hasPassword=false，只能验证码登录。
  • 注册与 OpenIM 注册解耦：先落 PG，再 outbox。OpenIM 挂了也不阻断注册。
  • 登录同样走 respondAuth：access 2h + refresh 30d。

相关接口

06建群 / 加群

对外群号是纯数字（如 100001），库内仍是 UUID。OpenIM groupID 同样是去连字符的内部 UUID。

sequenceDiagram
  autonumber
  participant App as 客户端
  participant H as GroupHandler

  App->>H: POST /groups {name, memberIds}
  H->>S: 去重、校验 UUID、人数≥3
  S->>PG: INSERT groups + members(owner/members)
  PG->>PG: Enqueue group.created

入群三条路径

  • POST /groups/:id/join：公开群直接进；审核群 409，必须走申请。
  • POST /groups/:id/invitations：群主/管理员邀请好友，直接写入成员并同步 OpenIM。
  • 二维码：resolve 只读 → join 按 joinMode 决定 enter / joined / pending_approval。

权限全在服务端

  • 改设置、禁言、踢人、解散：先查成员角色再执行。
  • 普通成员不能退成「群主退群」；解散只群主，状态变为 dismissed，所有接口不可见。
  • 全员禁言后普通成员发消息会被 Webhook BeforeGroup 拒绝。

08万人转发：HTTP 绝不循环发送

需求：单次至少 10000 好友、接收人互不可见、每人一份、重复提交不重复发。实现是「草稿任务 + PG Outbox + Kafka + Worker 限速」。

flowchart LR
  subgraph http [请求线程立刻返回]
    C[POST /forward-tasks 建草稿] --> A[add / generate 每批最多 1000]
    A --> S[POST /forward-tasks/submit]
    S --> OB[(forward_kafka_outbox)]
  end
  subgraph async [进程内后台]
    P[ForwardOutboxPublisher 2s 轮询] --> K[(Kafka Hash 按 taskId)]
    K --> W[ForwardWorker FetchMessage]
    W --> CL[ClaimTaskTargets SKIP LOCKED]
    CL --> POOL[Concurrency 默认 4]
    POOL --> QPS[Ticker 默认 20 QPS]
    QPS --> SEND[OpenIM SendForwardMessage]
    SEND --> ST[成功 / 跳过 / 重试 / 失败]
    ST -->|还有 pending| K
  end

幂等

客户端带 idempotencyKey。同一键若任务已离开 draft，直接返回原任务。发送用 sha256(taskId+targetUserId) 当 OpenIM clientMsgID，崩溃重试也不会给同一人再插一条。

过滤

TargetEligible 发送前再查：非好友、拉黑、封禁、已删除一律 skip。每个有效接收人只投一次。

Kafka 语义

Writer RequireAll 同步 ack；Reader 显式提交。先发 continue 事件再 commit，崩溃最多重复处理，靠锁和确定性 msgID 去重。毒消息解码失败直接提交，避免卡死分区。

09OpenIM：两条完全不同的通道

容易混淆的点：客户端聊天不走 Go WebSocket。Go 只在管理面用 REST，在控制面收 Webhook。

通道 A · 客户端 ↔ OpenIM

登录后 POST /im/token 拿到 token / apiAddr / wsAddr，SDK 直连 OpenIM。发消息、拉历史、会话、已读、撤回全部走这条。Go 不代理 WS。

通道 B · Go ↔ OpenIM 管理 API

internal/im/client.go 用 admin token 调 /user/* /friend/* /group/* /msg/*。HTTP 超时 10s，响应上限 2MB。OpenIM 可能 HTTP 200 但 errCode≠0，必须看业务码。

单聊拒绝原因

self / sender_inactive / account_inactive / blocked（双向） / not_friend。非好友即使 SDK 能发出去，服务端也会拦。

群聊拒绝原因

group_inactive / member_muted / group_muted（全员禁言时 owner/admin 仍可发）。非成员 JOIN 不到行，直接 not found。

Webhook 密钥配了但 OPENIM_WEBHOOK_ALLOW_CIDRS 为空时，authorized 恒为 false，回调全部 404——等于闸门失效。启动时会打 WARN。

12Outbox：业务写成功 ≠ OpenIM 已同步

所有用户/关系/群变更与 OpenIM 的一致性，靠同一事务写入 im_sync_outbox，再由 Worker 对账。这是抗抖、可水平扩展的核心。

stateDiagram-v2
  [*] --> pending: 业务事务提交
  pending --> processing: ClaimBatch SKIP LOCKED
  processing --> completed: EnsureUser/ImportFriends/EnsureGroup 成功
  processing --> retry: 失败 + 指数退避
  retry --> processing: next_attempt_at 到期
  processing --> dead: attempt ≥ 10
  dead --> processing: POST /internal/im/outbox/:id/replay
  processing --> processing: locked_at 超过 5 分钟视为租约过期再抢
event_typeWorker 动作
user.registered / user.profile_updatedEnsureUser（检查 → 注册或更新昵称头像）
friend.accepted / friend.deleted对照 PG 当前关系，Import 或双向 Delete
block.added / block.removedAddBlack / RemoveBlack
group.created/updated/member.*/mute/dismissed建群、补成员、改角色禁言、解散

运维接口：POST /internal/im/reconcile 把当前全量用户好友群重新入队；GET /internal/im/health 看 API、admin token、outbox 堆积。

13怎么扛高并发 —— 现有设计

策略可以概括成一句话：热路径不进 Go，冷路径异步化，写路径事务+租约，读路径分页+缓存。

1. 把最重的流量从 Go 上拿掉

消息不经业务 API

聊天是 OpenIM 长连接。万人同时说话时，压力在 msg-gateway / Mongo / Kafka，而不是 Gin。Go 只在每条消息上吃一次轻量 Webhook SQL。

文件不经业务 API

预签名直传 MinIO。头像、聊天图片的带宽与磁盘 I/O 不经过 Go 进程。

万人转发不经请求线程

Submit 只写 outbox 立刻返回。发送在 Worker 里按 QPS/并发限速，避免把 OpenIM 打穿。

2. 数据库侧

  • pgx 连接池 MaxConns=25，避免把 PostgreSQL 连接打满。
  • 列表接口强制 cursor + LIMIT（通讯录默认 50、最大 100）。
  • 多表写入必须事务；Outbox 与业务数据同事务，不会出现「好友已加但永远不同步」。
  • FOR UPDATE SKIP LOCKED：多实例 Worker 抢任务不会撞车，这是水平扩展转发/同步的基础。
  • 审计表 ON CONFLICT DO NOTHING，Webhook 重放不会堆重复行。

3. 缓存与锁

  • OpenIM 用户 Token：Redis + 进程内 map 双层；Redis 故障降级到本地缓存，接口不 5xx。
  • Admin Token 进程内缓存，避免每次管理调用都打 get_admin_token。
  • Token 按 user+platform 细粒度锁，不同用户并发签发互不影响。
  • 短信三维 Redis 限流；/health IP 限流。Redis 挂了限流放行，保证可用性优先。

4. 异步与背压

  • IMSyncWorker：2s poll，每批 20，最多 10 次，失败指数退避，死后进 dead letter。
  • ForwardWorker：默认 batch 50、concurrency 4、QPS 20（可环境变量调，concurrency 上限 256）。
  • Kafka Hash(taskId)：同一任务有序进同一分区，避免多消费者把同一任务打乱。
  • Webhook After 推送用 go dispatchPush，5s 超时，失败不影响 OpenIM 落库。
  • Webhook body 限制 64KB；OpenIM 响应限制 2MB，防止大包拖死进程。

5. 进程与部署层

  • Gin 每个请求一个 goroutine，适合大量短 REST。
  • ReadHeaderTimeout=10s 防慢速攻击；优雅退出 5s。
  • OpenIM compose：healthcheck + restart unless-stopped；etcd/kafka/mongo 挂卷，避免重启丢服务发现。
  • 基础设施可降级：没 Redis/MinIO/Kafka/OpenIM 时 HTTP 仍能起（对应能力 503 或 stub）。

14现状：能抗什么，还不能抗什么

文档必须诚实。下面这些是读代码后的结论，不是「理论上以后可以」。

已经具备的承载力

  • 消息扇出：交给 OpenIM，Go 不是瓶颈点。
  • 1 万+ 转发：异步 + 限速 + 幂等，HTTP 不会被同步发送拖死。
  • 关系同步：Outbox 可多实例，失败可重放。
  • 登录进聊天：Token 缓存避免 OpenIM 被重复签发打崩。

上生产前的真实瓶颈

  • MaxConns=25 对多副本 Gin 可能偏小或偏大，需要按实例数重算，目前写死。
  • Worker 与 API 同进程；流量高峰时同步任务会抢 CPU/连接。生产应拆独立 worker 部署。
  • compose 里 etcd/kafka 单节点，不是 HA。
  • 绝大多数 REST 没有 限流，只有 health 和短信。
  • 离线推送仍是 LoggingPushService，群消息 After 回调还会同步拉全量成员。
  • 注册 COUNT(*) 生成 publicId，并发注册不安全。
  • AuthHandler 未走分层，直接持有 *pgxpool.Pool。
  • 没有熔断/舱壁：OpenIM 超时会拖住 Token、建群补齐、Webhook 里 ListGroupMember。
若目标是「十万在线、每秒数千条消息」：扩 OpenIM msg-gateway / Mongo / Kafka 分区；Go 只保证 Webhook SQL 走索引、多副本 + 连接池、把 Worker 拆出去。不要试图让 Gin 再实现一套消息系统。
