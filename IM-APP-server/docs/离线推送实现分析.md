# 离线推送实现分析

> 对照参考站（https://qwa.11skrmx6.net）的「应用关掉仍能收到新消息通知」。  
> 本文只做实现分析，不改代码。阶段归属：架构 Phase 5；需求 11.5（Android / iOS 后台通知）。

## 1. 结论

参考站该功能是 **离线推送**（系统通知栏），不是 OpenIM 长连接。

当前项目：

- **在线收消息**：已接 OpenIM SDK WebSocket。
- **离线消息**：已由 OpenIM 落库，重新打开 App 可同步历史。
- **离线推送**：未真正下发。只有首次授权弹窗、设备 token 登记、后端 `LoggingPushService` 打日志。

要和网站用户体验对齐，必须补厂商推送通道（iOS APNs、Android FCM 或国内厂商通道），而不是再接一套聊天协议。

正式产品是 Android / iOS App（需求明确不做 H5 正式版）。对齐的是「杀掉 App 还能弹通知、点开进会话」，不是把网站的 Firebase Web + Service Worker 原样搬过来。

## 2. 三件事不要混

| 能力 | 谁负责 | 当前状态 | 用户感知 |
|---|---|---|---|
| 在线收消息 | OpenIM SDK 长连接 | 已接 | App 开着、进程活着，消息实时到达 |
| 离线消息 | OpenIM MongoDB + 上线同步 | 已有 | 杀进程后再打开，历史能补回来 |
| 离线推送 | 系统推送通道 | **未接通** | App 在后台或被杀掉，系统通知栏仍弹出 |

OpenIM 解决「消息别丢」；离线推送解决「人已经离开 App，还要被喊回来」。iOS 尤其不能指望后台一直挂着 WebSocket。

参考站实现（Web）：

1. 自定义询问「是否接收通知」，不在进页时直接调系统权限。
2. 用户确认后再 `Notification.requestPermission`，取 FCM token，报到后端。
3. 页面关闭后由 Service Worker 弹出系统通知；点击后打开对应会话。

我们的正式通道应是 **iOS APNs + Android FCM（海外）或个推/厂商通道（国内无 GMS）**。H5 FCM 只适合开发预览。

## 3. 当前链路（卡在哪）

```
发消息 → OpenIM 落库 → AfterMessage webhook → PushService.Dispatch
                                              ↓
                                     LoggingPushService 只打日志
```

已经具备：

- Redis 存 `platform / channel / deviceToken / enabled`（`POST/DELETE /api/v1/im/me/push-token`）
- 前端首次授权弹窗；确认后登记 token，取消后不再弹
- webhook 单聊用 `recvID`，群聊展开成员并排除发送方

缺口：

- 前端登记的多半是本机 `deviceId`，不是 FCM / APNs / uni-push 的真实 token（`manifest.json` 未开 Push 模块）
- `PushService` 是日志桩，没有调任何厂商 API
- webhook 不含消息正文，`PushMessage.Snippet` 为空
- 下发前不过滤：在线、全局免打扰、单会话静音、封禁/注销
- 真接下发会出现「人正在聊天，系统通知再弹一次」

相关代码：

- 后端：`internal/service/push.go`、`internal/handler/openim_webhook.go`、`cmd/server/main.go`
- 前端：`src/components/ImNotificationPermissionDialog.vue`、`src/utils/push-register.ts`、`src/utils/notification-permission.ts`
- 计划原文：[IM会话设置与消息推送接口开发计划.md](./IM会话设置与消息推送接口开发计划.md)

## 4. 架构选择：只走一条推送路径

不要让 OpenIM 自带离线推送和业务 webhook **同时真推**，否则会双条通知。

**建议沿用现有设计：业务后端推。**

```
OpenIM 落库 → AfterMessage → 业务 PushService
  → 查 Redis token、过滤免打扰/在线/封禁
  → 按 channel 调 APNs / FCM / 个推
```

理由：免打扰、封禁、群成员展开已在业务侧；token 接口和 webhook 骨架已在。

备选：打开 OpenIM 官方 FCM/APNs/个推模块，token 报到 OpenIM。业务过滤要再对一遍，会和现有 Redis token、webhook 重复，不建议并行。

万人转发 worker 目前固定 `notOfflinePush=true`。若群发也要响通知，需单独定策略，否则会打爆推送配额。

## 5. 后端要做的

把 `LoggingPushService` 换成真推送，并补上下发前判断。

### 5.1 厂商通道

| 平台 | 通道 | 说明 |
|---|---|---|
| iOS | APNs | 证书或 Token 鉴权 |
| Android 海外 | FCM HTTP v1 | 设备需 Google 服务 |
| Android 国内 | 个推 / 极光 + 华为/小米/OPPO/vivo | 无 GMS 时 FCM 不可用 |

密钥放环境变量，按 token 的 `channel` 分流：`apns` / `fcm` / `jpush` 等。

### 5.2 下发前过滤（现在没有）

对每个接收人：

- 账号已退出 / 封禁 / 注销 → 不推，并删除 token
- 没有 `enabled=true` 的 token → 不推
- 在线且 App 在前台 → 不推（查 OpenIM 在线状态，或让客户端上报前后台）
- 全局免打扰、单会话 `recvMsgOpt=1`、`recvMsgOpt=2` 且用户离线 → 不推
- 撤回、系统通知、自己发给自己 → 不推

`AfterMessage` 对每条消息都会回调，不挡在线用户就会和 SDK 提示音重复。

### 5.3 通知内容与跳转

- webhook 目前无正文：补摘要，或统一「你有一条新消息」
- payload 带 `conversationID` 或业务好友/群 ID，供点击进会话
- iOS `badge` 尽量用 OpenIM 未读总数
- 群聊已展开成员；大群要限流或合并，避免一人刷屏

### 5.4 Token 生命周期

- FCM `NotRegistered`、APNs BadDeviceToken → 删 Redis 对应记录
- 登出已有 `DELETE /im/me/push-token`；封禁/注销要服务端主动清
- 同一用户多设备：现有 Redis 列表已按 `platform + deviceToken` 去重

### 5.5 可靠性

Phase 5 规划用 Kafka 做推送任务更稳：webhook 只投递「要推」的事件，worker 再调厂商并重试。

第一版也可在 goroutine 里同步调厂商，但 webhook 必须继续快速 `allow`，不能拖死 OpenIM。推送失败不影响消息投递（现有约定保留）。

## 6. 前端要做的

授权弹窗只是入口。真正弹出系统通知，缺的是 **厂商 token** 和 **点击跳转**。

### 6.1 接入真正的推送 SDK（最大头）

当前 `uni.getPushClientId` 基本拿不到 cid，退回 `deviceId`，厂商无法投递。需选定并接入其一：

| 方案 | 适合 | 与现状 |
|---|---|---|
| uni-push 2.0（个推） | 国内 Android + iOS | 与现有 `getPushClientId` 最贴；manifest 需开 Push |
| 原生 FCM + APNs 插件 | 海外 | 更接近参考站 Firebase；国内 Android 差 |
| 个推 / 极光原生 SDK | 与后端同一家 | 前后端 channel 一致 |

没有这一步，后端接了 APNs/FCM 也推不到设备。自定义基座 / 云打包都要带 Push 模块。

### 6.2 确认后再登记真实 token

保持与参考站相同的顺序：

1. 自定义弹窗（已做）
2. 用户确认 → 申请系统通知权限（已做）
3. 取 FCM / APNs / cid（未做）
4. `POST /im/me/push-token`（接口已接，token 内容不对）

token 刷新要重报；系统权限被关掉要 `DELETE`。退出登录已会注销。

### 6.3 点击通知进对应会话

- App：`plus.push` / uni-push 的 click 回调，解析 payload，打开 `pages/chat/room`
- 冷启动（进程被杀再点通知）要单独处理，不能只写在页面 `onShow`
- 网站用 Service Worker + `BroadcastChannel`；App 没有 SW，这是原生点击回调

### 6.4 前台不要再弹系统通知

在线消息继续走 OpenIM + 应用内提示音（`chatSettings.sound` / `noDisturb`）。

上报前后台（`onShow` / `onHide`），或约定：前台只走 SDK，系统通知只给后台/被杀。

### 6.5 设置必须让后端能拦住

| 开关 | 现在 | 真推送时 |
|---|---|---|
| 新消息通知 | 本地 Pinia + token `enabled` | 关闭必须 `enabled=false` 或注销 token |
| 全局免打扰 | 本地为主 | 应写 OpenIM `PUT /im/me/global-msg-recv-opt` |
| 会话免打扰 | 已有会话设置接口 | 后端下发时读 `recvMsgOpt` |

只改客户端隐藏入口不算实现；需求要求服务端校验。

### 6.6 证书与系统权限

- iOS：Push Notifications 能力、APNs 证书或 Key、描述文件
- Android 13+：`POST_NOTIFICATIONS`（manifest 已声明）；还需通知渠道
- 本地标准运行基座通常没有推送，要用自定义基座或云打包包

### 6.7 H5（非正式范围）

若只想在浏览器里复刻参考站：Firebase 配置、`firebase-messaging-sw.js`、HTTPS、`getToken` 后登记 `platform=web`。与正式 App 是另一条线。

## 7. 职责边界

| 层 | 负责 | 不负责 |
|---|---|---|
| OpenIM | 在线消息、离线存储、上线同步、未读 | 不要再开一套官方离线推送（除非放弃业务 `PushService`） |
| Go 业务服务 | 何时推、推给谁、推什么、调哪家厂商、失效 token、封禁停推 | 不存聊天正文、不替代 SDK 长连接 |
| uni-app | 授权、拿真实 token、上报前后台、点通知进会话、前台不重复弹 | 不在页面里直连厂商 HTTP |

## 8. 验收（需求 11.5）

- [ ] Android：App 在后台或被杀掉，来私聊能弹出系统通知
- [ ] iOS：同上
- [ ] 点击通知进入对应会话（含冷启动）
- [ ] 全局免打扰 / 会话免打扰时不弹普通通知
- [ ] 退出、封禁或注销后不再向原账号推送
- [ ] 通知角标与 App 内未读大致一致

当前授权弹窗只能证明「用户同意接收」，不能证明「关 App 还能收到」。

## 9. 建议实施顺序

1. 选定推送供应商（uni-push / FCM+APNs / 个推），申请证书与控制台账号。
2. 前端接入 SDK，确认后上报**真实** token；点通知能进会话。
3. 后端替换日志桩：按 channel 下发；先做「不在线才推」和免打扰过滤。
4. 补失效 token 删除、封禁/注销停推、badge。
5. 需要再上 Kafka 重试与大群限流。
