# 私聊设置与用户举报接口部署说明

## 1. 本次发布内容

本次只增加后端能力，不要求同步修改前端：

- `GET /api/v1/report-reasons`：获取用户举报原因。
- `POST /api/v1/reports`：提交用户举报及证据文件。
- `GET /api/v1/im/conversations/:conversationId/settings`：读取单聊的置顶、免打扰、阅后即焚设置。
- `PATCH /api/v1/im/conversations/:conversationId/settings`：更新上述单聊设置。

数据库迁移文件为 `migrations/017_app_reports.sql`。它只处理以下三张管理后台共用表：

- `report_reasons`
- `reports`
- `report_files`

本次不会修改 `groups`、`group_members`、`group_reports` 等已有群组表。单聊设置直接保存在 OpenIM，不增加 PostgreSQL 字段。

## 2. 为什么必须先执行 SQL

新接口启动后会检查举报表所需字段。线上镜像若更新了程序但没有带上或执行 `017_app_reports.sql`，API 会拒绝启动并在日志中明确提示缺失字段，避免程序带着错误表结构继续提供服务。

PostgreSQL 的 `/docker-entrypoint-initdb.d/001_init.sql` 只在数据库数据卷第一次初始化时执行。线上已有数据卷时，即使更新这个文件也不会自动升级表结构，不能把它当作发布迁移方式。

`017_app_reports.sql` 已按以下情况设计：

- 新库没有举报表时创建完整表。
- 管理后台已经创建完整表时可重复执行。
- 历史环境只有部分表或部分字段时，用 `ADD COLUMN IF NOT EXISTS` 补齐字段。
- 整个脚本在事务中执行；任一步失败会整体回滚。

## 3. 上线前检查

以下命令均在服务器的 `IM-APP-server` 目录执行。示例使用 Compose 中的服务名 `postgres`、数据库用户 `im` 和数据库名 `im_app`；线上不同则按实际配置替换，不要复制示例密码。

先确认当前容器和数据库：

```bash
docker compose ps
docker compose exec -T postgres psql -U im -d im_app -v ON_ERROR_STOP=1 -c "SELECT current_database(), current_user, version();"
```

备份数据库，确认备份文件不为空后再继续：

```bash
mkdir -p backups
docker compose exec -T postgres pg_dump -U im -d im_app -Fc > "backups/im_app_before_017_$(date +%Y%m%d_%H%M%S).dump"
ls -lh backups/
```

记录当前 API 镜像，便于程序回退：

```bash
docker inspect im-app-api --format '{{.Image}}'
```

## 4. 正确发布顺序

### 第一步：更新代码并构建候选镜像

```bash
git pull --ff-only
docker compose build api
```

确认候选镜像内确实包含本次 SQL。缺少文件时禁止继续发布：

```bash
docker compose run --rm --no-deps --entrypoint sh api -c 'test -f /app/migrations/017_app_reports.sql && echo migration-ok'
```

### 第二步：单独执行 017 迁移

不要只重启 API 等它自动迁移。先在数据库容器仍稳定运行时手工执行，并启用遇错即停：

```bash
docker compose exec -T postgres psql -U im -d im_app -v ON_ERROR_STOP=1 < migrations/017_app_reports.sql
```

看到命令退出码为 `0` 且最后输出 `COMMIT`，才表示迁移成功。该脚本允许重复执行，所以 API 新容器启动时再次扫描到 017 不会重复创建数据。

### 第三步：核对关键字段

执行以下核对 SQL：

```bash
docker compose exec -T postgres psql -U im -d im_app -v ON_ERROR_STOP=1 <<'SQL'
WITH required(table_name, column_name) AS (
  VALUES
    ('report_reasons','id'), ('report_reasons','target_type'),
    ('report_reasons','reason'), ('report_reasons','language'),
    ('report_reasons','sort_order'), ('report_reasons','status'),
    ('reports','id'), ('reports','report_no'), ('reports','reporter_id'),
    ('reports','target_type'), ('reports','target_id'), ('reports','reason_id'),
    ('reports','reason_text'), ('reports','description'), ('reports','status'),
    ('reports','created_at'), ('reports','updated_at'),
    ('report_files','id'), ('report_files','report_id'), ('report_files','file_id'),
    ('report_files','file_url'), ('report_files','content_type'), ('report_files','created_at')
)
SELECT r.table_name, r.column_name AS missing_column
FROM required r
LEFT JOIN information_schema.columns c
  ON c.table_schema=current_schema()
 AND c.table_name=r.table_name
 AND c.column_name=r.column_name
WHERE c.column_name IS NULL;

SELECT reason, sort_order
FROM report_reasons
WHERE target_type='user' AND language='zh' AND status='active'
ORDER BY sort_order;
SQL
```

第一条查询必须返回 `0 rows`；第二条应至少看到本次预置的 6 个中文原因。若第一条有结果，不得启动新 API，应先检查 017 的错误输出和实际连接的数据库。

### 第四步：只替换 API

```bash
docker compose up -d --no-deps api
docker compose logs --tail=200 api
```

日志必须包含：

```text
migrations applied
```

若出现 `schema check`、`required database column ... is missing` 或 `required migration: 017_app_reports.sql`，说明镜像、工作目录或数据库不是刚才验证的那一套，不能继续放流量。

### 第五步：健康检查和接口冒烟

```bash
curl -fsS http://127.0.0.1:8080/health
curl -i -H "Authorization: Bearer <测试用户JWT>" \
  "http://127.0.0.1:8080/api/v1/report-reasons?targetType=user&language=zh"
```

再使用测试账号验证：

- 提交一条用户举报后，`reports` 中出现记录。
- 带证据举报时，证据文件属于当前测试账号且上传状态为 `ready`，`report_files` 中出现关联记录。
- OpenIM 已配置且测试账号已有单聊会话时，单聊设置 GET/PATCH 能读取和更新。

## 5. 接口调用示例

提交用户举报：

```bash
curl -X POST http://127.0.0.1:8080/api/v1/reports \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{
    "targetType":"user",
    "targetId":"<被举报用户UUID>",
    "reasonId":"<举报原因UUID>",
    "description":"测试举报",
    "evidenceFileIds":[]
  }'
```

更新单聊设置：

```bash
curl -X PATCH "http://127.0.0.1:8080/api/v1/im/conversations/<si_会话ID>/settings" \
  -H "Authorization: Bearer <JWT>" \
  -H "Content-Type: application/json" \
  -d '{"pinned":true,"doNotDisturb":true,"burnAfterRead":true,"burnDuration":30}'
```

`burnDuration` 单位为秒，启用阅后即焚时允许 `5～86400`。设置接口依赖 `OPENIM_API_URL`、`OPENIM_SECRET` 等现有 OpenIM 配置，不依赖新的业务库字段。

## 6. 回退原则

本次数据库变更是新增表、补字段和新增索引，对旧版 API 向后兼容。发生程序问题时：

1. 优先把 API 切回发布前记录的旧镜像。
2. 不要删除 `report_reasons`、`reports`、`report_files`，也不要删除新字段；保留它们不影响旧程序。
3. 只有数据库数据确实被错误修改且确认需要全库恢复时，才在维护窗口使用上线前备份恢复。全库恢复会覆盖发布后产生的新数据，必须单独评估。

禁止为了回退执行 `DROP TABLE`、`DROP COLUMN` 或清空 PostgreSQL 数据卷。

## 7. 本次不新增 Go 业务接口的页面项

- “图片与视频”“搜索聊天记录”“清除聊天记录”属于 OpenIM 消息和会话数据能力，应通过 OpenIM SDK 操作。
- 用户资料入口继续使用现有用户资料接口。
- 本次新增 Go 接口覆盖举报、置顶聊天、消息免打扰和阅后即焚。
